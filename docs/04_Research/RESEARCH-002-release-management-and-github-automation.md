## 1. Контекст, проблема и проверяемые гипотезы

### 1.1. Проблема
В методологии Docs-as-Code и харнессе `agent-docs-harness` жизненный цикл отдельных задач строго регламентирован тремя режимами:
* **Режим 1 (`/kb-plan`):** Концепция, риски, Q&A, архитектурный план `PLAN-XXX`.
* **Режим 2 (`/kb-task`):** Техническая спецификация `TASK-XXX` с файловыми контрактами и планом верификации.
* **Режим 3 (`/kb-implement` и `/kb-complete`):** Реализация, верификация, закрытие карточки на Канбане, отметка чекбокса в `Roadmap.md` и запись в `Devlog.md`.

Задачи логически сгруппированы в **Фазы** в `Roadmap.md` (например, *Фаза 1: MVP*, *Фаза 2: Расширения и экосистема*, *Фаза 3: Зрелость инсталлятора*).

Однако на границе **завершения фазы** в текущем рабочем процессе образуется системный разрыв:
1. **Отсутствие релизного перехода:** Когда закрывается последняя задача фазы, фаза считается выполненной, но процесс не производит формального релизного артефакта. Нет фиксации того, что вошло в релиз, какой тег присвоен версии, где находятся скомпилированные бинарники и как пользователю получить релизный пакет.
2. **Дилемма среды (GitHub vs Local-Only):**
   * Часть проектов хостится на GitHub и требует создания **GitHub Release** с прикрепленными дистрибутивами, релизными заметками (Release Notes) и аннотированным Git-тегом (`vX.Y.Z`).
   * Другая часть проектов разрабатывается в **Local-Only режиме** (изолированные корпоративные сети, оффлайн-разработка, локальные хобби-проекты без удаленного репозитория). Для них облачный GitHub Release недоступен, но критически необходима локальная сборка релизного файла с точным указанием пути (например, `dist/app-v1.0.0.zip`), размера и контрольной суммы SHA-256.
3. **Гетерогенность технологических стеков:** Шаблоны харнесса поддерживают Apple Swift, TypeScript/Node/Web, Python, .NET, Generic. Каждый стек собирает релизы по-своему (Swift: `swift build -c release` / Xcode archive, Python: `python -m build`, TS: `npm run build`, .NET: `dotnet publish -c Release`).
4. **Вопрос триггера:** Должен ли релиз создаваться **автоматически** при завершении фазы (внутри `/kb-complete`), либо процесс должен запускаться **явно через специализированный скилл** (`/kb-release`)?

### 1.2. Проверяемые гипотезы
* **Гипотеза 1 (Триггер процесса):** Автоматический неявный запуск релиза при закрытии последней задачи фазы нарушает принцип наименьшего удивления (POLA), блокирует приемочное тестирование и несет высокий риск публикации дефектов. Явная команда (`/kb-release`) с предварительной проверкой чек-листов (Pre-flight checks) обеспечивает безопасность и управляемость.
* **Гипотеза 2 (Архитектура Dual-Mode):** Процесс релиза должен быть двухуровневым и одинаково устойчиво работать как с GitHub (через `gh` CLI или CI-теги), так и в Local-Only режиме (локальный каталог `dist/`, вычисление SHA-256 хэшей и фиксация путей в локальной документации).
* **Гипотеза 3 (Контракт сборщика — Convention over Configuration):** Харнесс не должен хардкодить тонкости компиляции десятков языков программирования. Вместо этого вводится стандартизованный контракт релизной сборки (Build Hook Contract): скрипт или команда проекта (например, `scripts/build_release.py` или `npm run build`), помещающий артефакты в предсказуемый каталог `dist/`.
* **Гипотеза 4 (Синхронизация базы знаний):** Релиз должен быть полноправным объектом базы знаний Docs-as-Code: отдельный шаблон `TEMPLATE_RELEASE.md`, постоянный документ `docs/02_Tasks/Releases/RELEASE-vX.Y.Z.md`, обновление корневого `CHANGELOG.md` и перелинковка в `Roadmap.md`.

## 2. Анализ механизмов платформы и критический стресс-тест

### 2.1. Стресс-тест триггера: Неявный авторелиз vs Явная команда `/kb-release`

Проведем проверку идеи «*автоматически создавать релиз при закрытии последней задачи фазы в `kb-complete`*» с позиции **Devil's Advocate**:

```
[Закрытие последней задачи: kb-complete TASK-008]
                        │
                        ▼
      ⚠️ Попытка неявного авторелиза?
   ┌────────────────────────────────────────┐
   │ 1. E2E тестирование еще не проводилось! │
   │ 2. Ошибка сборщика ломает закрытие ТЗ │
   │ 3. SemVer (мажор/минор) неизвестен      │
   │ 4. Сборка занимает 10-20 минут         │
   │ 5. Публичный релиз уходит без аппрува   │
   └────────────────────────────────────────┘
```

#### Факторы отказа неявного авторелиза:
1. **Нарушение жизненного цикла приемочного тестирования (`05_Testing/`):**
   Согласно канону Docs-as-Code, после завершения реализации всех задач фазы проводится сквозное приемочное тестирование (E2E UX). В ходе тестирования с высокой вероятностью выявляются краевые дефекты (`BUG-XXX`) или шероховатости интерфейса. Если релиз публикуется автоматически при закрытии `TASK-008`, в продуктив или на GitHub уходит недотестированная версия, которую затем придется экстренно патчить.
2. **Blast Radius (Радиус поражения ошибки):**
   Релизная сборка — ресурсоемкая операция, зависящая от компиляторов, окружения, сертификатов подписи (Apple Developer ID, Authenticode, GPG) и сетевых токенов. Если во время выполнения `/kb-complete TASK-008` сборочный скрипт упадет с ошибкой (например, истек сертификат или отсутствует токен GitHub), задача `TASK-008` останется в подвешенном состоянии: код написан, тесты задачи пройдены, но Канбан и Devlog не обновятся из-за сбоя внешнего релизного шага.
3. **Неопределенность версии (SemVer Ambigiuty):**
   Автоматика не может самостоятельно определить, завершилась ли фаза выпуском `v1.0.0` (мажорный релиз с breaking changes), `v0.2.0` (минорный функционал) или `v0.1.1` (патч). Решение о версии требует человеческого или агентно-стратегического намерения.
4. **Принцип наименьшего удивления (Principle of Least Astonishment):**
   Завершение локальной инженерной задачи (`/kb-complete`) не должно вызывать глобальных сайд-эффектов (создание публичного Git-тега, рассылка вебхуков подписчикам GitHub, деплой).

**Вердикт по триггеру:**  
Автоматический запуск релиза внутри `kb-complete` — **категорический анти-паттерн**.  
Релиз должен инициироваться **строго явно** через специализированный скилл `/kb-release`.  
*Компромиссная эргономика:* При закрытии последней задачи фазы `kb-complete` выводит информативную подсказку (Nudge):
> `💡 Все задачи Фазы 2 завершены! Рекомендуется выполнить приемочные сценарии в docs/05_Testing/ и запустить команду /kb-release v0.2.0 для подготовки релизного пакета.`

### 2.2. Архитектура публикации: GitHub Releases vs Local-Only

Проекты функционируют в принципиально разных сетевых и инфраструктурных контекстах:

| Аспект | GitHub Mode (Remote / Open Source) | Local-Only Mode (Offline / Enterprise) |
| :--- | :--- | :--- |
| **Система контроля версий** | Git с настроенным `origin` на github.com | Git без `origin` (локальный) либо без Git |
| **Инструмент публикации** | `gh release create` или GitHub Actions CI | Локальная файловая система, сборка в `dist/` |
| **Релизный артефакт** | Asset, прикрепленный к GitHub Release | Локальный архив/бинарник в каталоге `dist/` |
| **Идентификатор релиза** | Git Tag (`vX.Y.Z`) + Web URL релиза | Локальный файл `RELEASE-vX.Y.Z.md` + SHA-256 |
| **Аутентификация** | `GITHUB_TOKEN` / `gh auth status` | Не требуется |

#### Риски и ограничения платформ:
1. **GitHub CLI (`gh`):**
   * Утилита `gh` может отсутствовать в системе пользователя (`gh: command not found`).
   * Утилита может быть установлена, но не авторизована (`gh auth status` возвращает код != 0).
   * Репозиторий может быть приватным, а токен не иметь прав `repo` / `contents: write`.
   * *Требование устойчивости:* Скилл `/kb-release` должен проверять наличие и статус `gh`. Если `gh` недоступен, процесс не должен падать с ошибкой, а обязан выполнить элегантную деградацию (graceful fallback): создать локальный git-тег, сформировать локальный релизный файл и вывести инструкцию для ручной публикации.
2. **Безопасность секретов и подписи кода (Code Signing):**
   * В современной индустрии сборка финальных бинарников с боевыми сертификатами подписи (Apple Gatekeeper, Windows SmartScreen) на машине рядового разработчика считается уязвимой практикой.
   * **Золотой стандарт CI/CD:** Агент на локальной машине готовит релизные заметки, бампает версию, формирует `RELEASE-vX.Y.Z.md` и пушит тег `vX.Y.Z`. А сборку релизных бинарников и публикацию ассетов в GitHub Release выполняет изолированный **GitHub Actions Workflow** с защищенными репозиторными секретами (`secrets.CERTIFICATE_BASE64`, OIDC).
   * Для локальных проектов без CI агент выполняет локальный сборочный хук и фиксирует хэш артефакта.

### 2.3. Гетерогенность стеков: Build Hook Contract

Разные языки компилируют и упаковывают релизы абсолютно по-разному:
* **Python:** `python -m build` -> `dist/*.whl`, `dist/*.tar.gz`, либо PyInstaller -> `dist/app.exe`.
* **Apple Swift / macOS / iOS:** `swift build -c release` -> `.build/release/`, либо `xcodebuild -scheme App -configuration Release archive` -> `.xcarchive` / `.dmg`.
* **TypeScript / Node / Frontend:** `npm run build` -> `dist/` или `build/`.
* **.NET (C# / F#):** `dotnet publish -c Release -o ./dist`.
* **Rust:** `cargo build --release` -> `target/release/`.
* **agent-docs-harness (наш собственный репозиторий):** `python scripts/build_installer.py` -> `install.py`.

Попытка захардкодить команды всех возможных компиляторов в утилиту релиза приведет к раздуванию кода, хрупкости и невозможности учесть миллионы пользовательских флагов компиляции.

#### Решение: Конвенция контракта сборки (Convention over Configuration)
Устанавливается единый стандарт для проектов:
1. **Стандартный выходной каталог:** Все релизные файлы приложения складываются в каталог `dist/` в корне проекта (добавлен в `.gitignore`).
2. **Точка входа сборки (Build Hook Discovery):**
   Скилл `/kb-release` ищет команду сборки по цепочке приоритетов:
   1. Специфичный скрипт сборки проекта: `scripts/build_release.py` или `scripts/build_release.sh`.
   2. Конфиг проекта:
      - `package.json` -> скрипт `npm run build` или `npm run release`.
      - `Makefile` -> таргет `make release` или `make build`.
      - `pyproject.toml` / `setup.py` -> `python -m build`.
      - `Package.swift` -> `swift build -c release`.
      - `Cargo.toml` -> `cargo build --release`.
      - `*.csproj` / `*.sln` -> `dotnet publish -c Release -o ./dist`.
   3. Если ни один хук не найден — сборка бинарника пропускается с понятным предупреждением, а формируется документальный релиз (Source Release: Git Tag + Release Notes).

## 3. Практические эксперименты и прототипы

### 3.1. Эксперимент 1: Детекция среды и graceful fallback для GitHub
Проверим логику определения возможностей окружения (наличие Git remote, авторизация `gh`, режим Local-Only) на стандартной библиотеке Python.

```python
import subprocess
import shutil

def detect_release_environment():
    status = {
        "has_git": False,
        "has_remote": False,
        "remote_url": None,
        "has_gh_cli": False,
        "gh_authenticated": False,
        "mode": "local-only"
    }
    
    # 1. Проверка git
    if shutil.which("git"):
        try:
            res = subprocess.run(["git", "rev-parse", "--is-inside-work-tree"],
                                 capture_output=True, text=True, check=False)
            if res.returncode == 0:
                status["has_git"] = True
                
                # Проверка remote origin
                remote_res = subprocess.run(["git", "remote", "get-url", "origin"],
                                            capture_output=True, text=True, check=False)
                if remote_res.returncode == 0:
                    status["has_remote"] = True
                    status["remote_url"] = remote_res.stdout.strip()
        except Exception:
            pass

    # 2. Проверка gh CLI
    if shutil.which("gh"):
        status["has_gh_cli"] = True
        try:
            auth_res = subprocess.run(["gh", "auth", "status"],
                                      capture_output=True, text=True, check=False)
            if auth_res.returncode == 0:
                status["gh_authenticated"] = True
        except Exception:
            pass

    # 3. Итоговый режим
    if status["has_remote"] and ("github.com" in (status["remote_url"] or "")):
        status["mode"] = "github"
    else:
        status["mode"] = "local-only"

    return status
```

**Результат стресс-теста:**  
Скрипт мгновенно (< 50мс) определяет среду без сторонних зависимостей. Если репозиторий оффлайн или `gh` не залогинен, процесс автоматически переключается в `local-only` режим без крашей.

### 3.2. Эксперимент 2: Сканирование артефактов и расчет SHA-256

Для локальных релизов критически важно гарантировать целостность файлов и предоставить разработчику точные сведения об артефактах:

```python
import hashlib
from pathlib import Path

def inspect_release_artifacts(dist_dir="dist"):
    dist_path = Path(dist_dir)
    if not dist_path.exists() or not dist_path.is_dir():
        return []

    artifacts = []
    for file_path in sorted(dist_path.iterdir()):
        if file_path.is_file() and not file_path.name.startswith("."):
            hasher = hashlib.sha256()
            size_bytes = file_path.stat().st_size
            with open(file_path, "rb") as f:
                while chunk := f.read(65536):
                    hasher.update(chunk)
            
            size_mb = size_bytes / (1024 * 1024)
            size_str = f"{size_mb:.2f} MB" if size_mb >= 1 else f"{size_bytes / 1024:.1f} KB"
            
            artifacts.append({
                "name": file_path.name,
                "path": str(file_path.as_posix()),
                "size": size_str,
                "sha256": hasher.hexdigest()
            })
    return artifacts
```

**Формируемый блок Markdown для релизного файла:**

```markdown
### 📦 Релизные артефакты (Distribution Packages)

| Файл | Размер | Контрольная сумма (SHA-256) | Расположение |
| :--- | :--- | :--- | :--- |
| `agent-docs-harness-v0.2.0.zip` | 1.45 MB | `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` | `dist/agent-docs-harness-v0.2.0.zip` |
| `install.py` | 185.2 KB | `8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4` | `install.py` |
```

### 3.3. Эксперимент 3: Автоматическая агрегация Release Notes из базы знаний

В отличие от традиционных инструментов, которые генерируют changelog исключительно из однострочных коммитов Git (где часто встречается шум вида `fix typo`, `wip`), харнесс Docs-as-Code обладает полной семантической базой:
* **Завершенные ТЗ фазы:** `docs/02_Tasks/Specs/<Phase>/TASK-XXX-*.md` содержат цель, решенные проблемы и созданные файлы.
* **Закрытые дефекты:** `docs/02_Tasks/Bugs/BUG-XXX-*.md` содержат RCA и описание устраненной ошибки.
* **Принятые ADR фазы:** `docs/03_Decisions_ADR/ADR-XXXX-*.md` содержат обоснование архитектурных новшеств.

Скрипт или агент может мгновенно сгенерировать содержательные, структурированные заметки о выпуске:


## 4. Сравнительный анализ альтернатив (Trade-off Matrix)

Сравним 4 потенциальных подхода к реализации релизного процесса:

| Критерий | 1. Неявный авторелиз в `kb-complete` | 2. Внешний инструмент (semantic-release / goreleaser) | 3. Pure Git-Tag CI (только тег, всё в облаке) | 4. Гибридный скилл `/kb-release` (Dual-Mode) — **Рекомендованный** |
| :--- | :--- | :--- | :--- | :--- |
| **Управляемость и контроль** | 🔴 Низкая (неожиданные сайд-эффекты) | 🟡 Средняя (требует строгих conventional commits) | 🟢 Высокая (ручной пуш тега) | 🟢 Максимальная (интерактивный префлайт и подтверждение) |
| **Zero Dependencies (ADR-0001)** | 🟢 Полная (встроено) | 🔴 Провал (требует Node.js / Go / npm зависимости) | 🟢 Полная (только Git) | 🟢 Полная (стандартная библиотека Python) |
| **Поддержка Local-Only / Offline** | 🟡 Частичная | 🔴 Слабая (заточен под npm/GitHub) | 🔴 Нулевая (зависит от GitHub Actions) | 🟢 Идеальная (локальный `dist/`, SHA-256, локальный релиз-файл) |
| **Поддержка GitHub Releases** | 🟡 Ограниченная | 🟢 Отличная | 🟢 Отличная | 🟢 Отличная (через `gh` CLI или CI) |
| **Интеграция с Docs-as-Code** | 🔴 Размыта (смешивает задачу и релиз) | 🔴 Отсутствует (не знает про `TASK-XXX` и `Roadmap`) | 🔴 Отсутствует | 🟢 Нативная (`Releases/`, `Roadmap.md`, `CHANGELOG.md`) |
| **Изоляция сбоев (Blast Radius)** | 🔴 Высокий риск (сбой сборки блокирует задачу) | 🟡 Средний | 🟢 Нулевой (сборка изолирована в CI) | 🟢 Нулевой (релиз отделен от закрытия задач) |
| **Возможность E2E UX тестирования** | 🔴 Отсутствует (релиз уходит до тестов) | 🟡 Требует сложных пайплайнов | 🟢 Ручной контроль | 🟢 Префлайт-проверка чеклиста `05_Testing/` |

## 5. Отвергнутые подходы и «кладбище идей» (Rejected Alternatives)

* ❌ **Отвергнуто: Автоматический неявный релиз при закрытии последней задачи в `kb-complete`:**  
  *Причина отказа:* Нарушает принцип наименьшего удивления, исключает возможность проведения E2E UX тестирования фазы до момента публикации, блокирует закрытие задачи при сбоях компилятора или сети, лишает разработчика выбора номера версии SemVer.
* ❌ **Отвергнуто: Интеграция сторонних утилит релизов (`semantic-release`, `release-it`, `standard-version`):**  
  *Причина отказа:* Прямое нарушение фундаментального принципа [[../03_Decisions_ADR/ADR-0001-zero-dependencies-python-stdlib|ADR-0001]] (Zero External Dependencies). В проектах на Swift, Python или .NET недопустимо требовать установку Node.js и npm-пакетов только ради выпуска релиза.
* ❌ **Отвергнуто: Хранение бинарных артефактов внутри Git-репозитория:**  
  *Причина отказа:* Коммит архивов, DMG или EXE файлов в репозиторий раздувает размер папки `.git`, замедляет клонирование и нарушает лимиты GitHub (100 MB на файл). Каталог `dist/` должен быть строго в `.gitignore`, а распространение файлов должно идти через GitHub Release Assets либо локальную файловую систему.
* ❌ **Отвергнуто: Хардкод сборочных команд для всех компиляторов в ядро харнесса:**  
  *Причина отказа:* Невозможно предусмотреть все конфигурации флагов Xcode, MSBuild, Webpack, Vite, Cargo. Вместо этого утвержден декларативный Build Hook Contract (`scripts/build_release.py` или секция в конфиге проекта).

## 6. Выводы и целевая архитектура релиза

### 6.1. Рекомендованное решение: Скилл `/kb-release` и инфраструктура релиза

Для реализации полноценного и безопасного процесса релиза при завершении фазы рекомендуется внедрить следующую архитектуру:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Жизненный цикл Фазы                             │
│                                                                        │
│  [TASK-001] ──► [TASK-002] ──► [TASK-00N] (через /kb-complete)        │
│                                     │                                  │
│                                     ▼                                  │
│                  💡 Подсказка: Фаза завершена!                         │
│                                     │                                  │
│                                     ▼                                  │
│             [Приемочное E2E тестирование в docs/05_Testing/]           │
│                                     │                                  │
│                                     ▼                                  │
│                  🟢 Запуск: /kb-release <vX.Y.Z>                       │
└─────────────────────────────────────┬──────────────────────────────────┘
                                      │
            ┌─────────────────────────┴─────────────────────────┐
            ▼                                                   ▼
┌───────────────────────────────┐   ┌───────────────────────────────────┐
│     Режим 1: GitHub / CI      │   │       Режим 2: Local-Only         │
│                               │   │                                   │
│ • Проверка чистой ветки git   │   │ • Вызов локального build-хука     │
│ • Генерация RELEASE-vX.Y.Z.md │   │ • Сборка артефакта в dist/        │
│ • Синхронизация CHANGELOG.md  │   │ • Расчет хэшей SHA-256 и размера  │
│ • Создание Git тега vX.Y.Z    │   │ • Фиксация путей к файлам         │
│ • Публикация gh release       │   │ • Обновление Roadmap и Devlog     │
│   (или триггер release.yml)   │   │ • Статус: Готов локально          │
└───────────────────────────────┘   └───────────────────────────────────┘
```

### 6.2. Компоненты для внедрения в проект
1. **Канонический шаблон релиза:** Создать `docs/00_Templates/TEMPLATE_RELEASE.md` (метаданные, чейнджлог, таблица артефактов, контрольные суммы, статус).
2. **Директория постоянного хранения релизов:** Создать `docs/02_Tasks/Releases/` с правилом неизменяемости ссылок (Permalinks).
3. **Исполняемый скилл `/kb-release`:** Разместить `.agents/skills/kb-release/SKILL.md` с пошаговой процедурой:
   * **Шаг 1. Pre-flight Check:** Проверка, что все задачи фазы закрыты в `Roadmap.md`, баги в `Bugs/` устранены, `kb_lint.py` проходит с кодом 0, тесты зеленые, рабочее дерево Git чистое.
   * **Шаг 2. Агрегация Release Notes:** Сбор заголовков и ссылок из `TASK-XXX`, `BUG-XXX`, `ADR-XXXX` фазы.
   * **Шаг 3. Исполнение сборки артефактов:** Вызов сборочного контракта (при наличии) и сборка в `dist/`.
   * **Шаг 4. Фиксация документов:** Создание `docs/02_Tasks/Releases/RELEASE-vX.Y.Z.md`, обновление `CHANGELOG.md`, перевод фазы в `Roadmap.md` в статус `✅ Завершена (Релиз: RELEASE-vX.Y.Z)`, запись в `Devlog.md`.
   * **Шаг 5. Публикация:**
     * Если GitHub доступен: `git tag -a vX.Y.Z -m "..."`, `git push origin vX.Y.Z`, создание релиза через `gh release create vX.Y.Z dist/* --notes-file ...`.
     * Если Local-Only: локальный тег, вывод точного локального пути к файлу в консоль и завершение.
4. **Утилита сборки/хеширования:** Включить функционал в `scripts/kb_release.py` (или расширение CLI инсталлятора).
5. **Шаблон GitHub Actions:** Добавить `.github/workflows/release.yml` в библиотеку шаблонов инсталлятора для автоматической облачной сборки по тегам `v*`.
