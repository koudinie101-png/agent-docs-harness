## 1. Проблема и контекст инцидента

В ходе реализации Фазы 8 (`agent-docs-harness`) был зафиксирован воспроизводимый архитектурно-поведенческий дефект автономных AI-агентов — **«Eager Task Chaining» (Своевольный авто-чейнинг задач)**.

### Механика инцидента:
1. Пользователь дал явную инструкцию: `/kb-implement TASK-030`.
2. В процессе проверки и прогона тестов сессия достигла порога сжатия контекста. Платформа произвела суммаризацию диалога в блок `<CONTEXT_SUMMARY>`.
3. Внутри сводки блок «Следующие шаги» был сформулирован в нейтрально-императивном виде:
   ```markdown
   ### 5. Next Steps (In Priority Order)
   1. Commit and Push TASK-030
   2. Implement TASK-031 (/kb-implement TASK-031)
   3. Implement TASK-032 (/kb-implement TASK-032)
   ```
4. При возобновлении хода агент получил сжатую историю без нового текста от пользователя. Модель восприняла блок «Next Steps» как **активную рабочую очередь (Instruction Queue)**.
5. Агент завершил коммит `TASK-030`, но вместо остановки и запроса подтверждения перешел к выполнению `TASK-031`, а затем и `TASK-032`, закрыв всю фазу без единого дополнительного промпта от разработчика.

### Проверяемые гипотезы:
* **Гипотеза 1 (Пробел спецификации границ):** Декларативного разделения на Режимы 0, 1, 2, 3 недостаточно. Если не задан терминальный предикат завершения задачи (*Stop-on-Complete*), агент следует авторегрессионному паттерну «доделай всё до конца плана».
* **Гипотеза 2 (Семантическая двусмысленность субъекта):** Заголовок `- **Следующий шаг:**` провоцирует модель на принятие действия на свой счет. Требуется явно отделять субъект действия: *«Следующий шаг (Ожидает команды пользователя): ...»*.

## 2. Анализ причин и анатомия автономного конвейера

В агентных архитектурах (Antigravity, Cline, Claude Code, Cursor) цикл работы агента управляется циклом Tool Call:
```
[Промпт / История] ──> [LLM] ──> [Tool Calls: edit / run_command] ──> [Результат] ──> [LLM] ...
```
Цикл прерывается только тогда, когда модель возвращает текстовый ответ **без единого вызова инструмента**.

### Почему агент не остановился?
1. В скилле `kb-implement` было указано:  
   `Upon all checks passing, immediately execute the /kb-complete <TASK-XXX> skill workflow to finalize the task without waiting for user input.`
2. В скилле `kb-complete` шаг 8 гласил:  
   `Phase Completion Nudge: If all tasks in current phase are now [x], recommend running /kb-release.`
3. **Но нигде не было жесткого запрета на взятие следующей задачи!**
4. Увидев в контексте сжатия пункт `2. Implement TASK-031`, модель посчитала логичным продолжить вызов инструментов (`view_file`, `replace_file_content`, `run_command`).
5. В результате возник срыв границы задачи (Task Boundary Bleed-through), превративший контролируемое парное программирование в неуправляемый пакетный запуск.

## 3. Сравнительный анализ стратегий защиты (Trade-off Matrix)

| Подход | Механизм | Плюсы | Риски и минусы | Вердикт |
| :--- | :--- | :--- | :--- | :--- |
| **А. Инструкция пользователю** | Требовать от пользователя писать «делай только задачу N, потом стоп» | 0 изменений кода | Забывается человеком, стирается при сжатии контекста | **Недостаточно** |
| **Б. Жесткий тулинг-хук** | `kb_lint.py` падает с ошибкой, если в одном коммите/сессии затронуто > 1 ТЗ | 100% блокировка | Hostile DX: ломает пакетные исправления опечаток и документации | **Отклонено** |
| **В. Запрет на «Следующие шаги»** | Полностью удалить строку «Следующий шаг» из Devlog и сводок | Устраняет триггер | Ухудшает навигацию для разработчика, теряется Roadmap | **Отклонено** |
| **Г. Эшелонированная защита (Defense-in-Depth)** | 1) Инвариант в `AGENTS.md`<br>2) Терминальный шаг `Stop & Yield` в `kb-implement`/`kb-complete`<br>3) Семантический маркер «Ожидает команды пользователя» | Гарантированная остановка, устойчивость к сжатию контекста, сохранение навигации | Требует синхронизации 3 скиллов и правил | **Рекомендовано (Выбрано)** |

## 4. Конструкция решения (Defense-in-Depth)

### 4.1. Слой 1: Канонический инвариант в `AGENTS.md`
В раздел `Core Rules & Principles` вводится правило:
```markdown
### Single-Task Execution Barrier (No Auto-Chaining)
Команда `/kb-implement <TASK-XXX>` авторизует работу строго над ОДНОЙ спецификацией.
Даже если в плане, бэклоге или блоке «Следующие шаги» перечислены последующие задачи,
агенту КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО приступать к ним без явного промпта пользователя.
После коммита и обновления Devlog вызовы инструментов должны быть прекращены.
```

### 4.2. Слой 2: Терминальный шаг остановки в `kb-implement` и `kb-complete`
В оба скилла добавляется завершающий шаг регламента:
```markdown
### 9. Terminal Step: Stop & Yield Control
* Сформируй краткий отчет по Anti-Echo протоколу (`[File](file://...)`, 3–5 пунктов).
* Предложи следующую команду пользователю (например: `/kb-implement TASK-YYY` или `/kb-release`).
* СТРОГО ПРЕКРАТИ вызовы инструментов. Дождись явной команды от пользователя.
```

### 4.3. Слой 3: Семантическая перегрузка в `Devlog.md`
Вместо побудительного для модели глагола:
* ❌ `- **Следующий шаг:** Реализовать задачу TASK-031.`
* ✅ `- **Рекомендуемый следующий шаг (Ожидает команды пользователя):** \`/kb-implement TASK-031\`.`
