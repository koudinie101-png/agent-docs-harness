## 1. Контекст, проблема и проверяемые гипотезы

### 1.1. Контекст и системные разрывы
В текущей реализации харнесса Docs-as-Code предполагается два типовых сценария установки (`install.py`):
1. **Brownfield (существующий проект):** в репозитории уже есть файлы проекта (`package.json`, `requirements.txt` и т.д.), по которым утилита автоматически определяет стек технологий.
2. **Greenfield с заранее известным стеком:** при чистой установке пользователю предлагается выбрать стек из жесткого списка (`swift`, `ts`, `python`, `dotnet`, `generic`).

Однако на практике в AI-ассистированной разработке часто возникает третий сценарий:
* **Сценарий 0: «Абсолютный Greenfield / Старт от сырой идеи» (Idea-First Greenfield):**
  У пользователя есть пустая папка и лишь вербальная идея приложения (например: *«Хочу легковесный кроссплатформенный демон мониторинга батареи»* или *«Сервис синхронизации локальных заметок с шифрованием»*).
  Стек технологий **объективно неизвестен на старте**! Выбор между Rust, Swift, Go, Python или TypeScript является архитектурной дилеммой, которую необходимо сначала исследовать и обосновать.
  Принудительный выбор стека в `install.py` генерирует фиктивные заглушки в `SPEC.md` и кодовые сниппеты в шаблонах, которые затем приходится переписывать вручную.

Второй системный разрыв возникает на стадии активной разработки:
* **Проблема дрифта спецификации (Documentation Drift / Rotten Spec):**
  В начале проекта генерируются стартовые файлы `SPEC.md` и `README.md`. В процессе реализации фаз (Фазы 1–5+) функционал системы существенно расширяется, меняются внешние контракты, добавляются новые CLI-команды и архитектурные решения.
  Поскольку задачи `TASK-XXX` изолированы и содержат локальные файловые контракты (`[NEW]`, `[MODIFY]`), агенты по умолчанию не трогают корневой `SPEC.md` и `README.md`. В результате `SPEC.md` превращается в устаревший памятник первой недели разработки, переставая быть Мастер-Спецификацией и Единым Источником Истины (Single Source of Truth).

### 1.2. Проверяемые гипотезы
* **Гипотеза 1 (Пресет Idea-First / Отложенный стек в `install.py`):** Добавление в `install.py` пресета стека `undecided` (или флага `--idea "<описание>"`) позволяет инициализировать чистый харнесс без навязывания фиктивного языка, фиксируя идею как рабочую гипотезу в `SPEC.md` со статусом `status: discovery` и направляя агента сразу в Режим 0 (`/kb-research`).
* **Гипотеза 2 (Синтез `SPEC.md` и `README.md` по итогам Режима 0):** Завершение первого исследования Режима 0 (`RESEARCH-001` + `ADR-0001` по выбору стека) должно автоматически кристаллизовать Мастер-Спецификацию (`SPEC.md`) и витрину проекта (`README.md`), переводя проект из состояния "Discovery" в состояние "Ready for Planning".
* **Гипотеза 3 (Инвариант Живой Спецификации — Living Spec Invariant):** Корневые документы `SPEC.md` и `README.md` должны иметь регламентированные точки актуализации в жизненном цикле:
  - На уровне релиза фазы (`/kb-release`) через обязательный префлайт-чек актуализации `README.md` и `SPEC.md`.
  - На уровне завершения задач (`/kb-complete`), если задача меняет внешние интерфейсы, контракты или стек.
* **Гипотеза 4 (Контроль дрифта через `kb_lint.py`):** В линтер `kb_lint.py` можно добавить неблокирующую эвристическую проверку (warning): если в `Roadmap.md` закрыты 2+ фазы, а дата обновления `SPEC.md` или `README.md` совпадает с датой инициализации проекта, линтер выводит напоминание о необходимости актуализации Мастер-Спецификации.

## 2. Анализ сценариев и архитектурных механизмов

### 2.1. Воронка от Сырой Идеи к Мастер-Спецификации (Idea-to-Spec Pipeline)

```
        ШАГ 1: ИНИЦИАЛИЗАЦИЯ                       ШАГ 2: РЕЖИМ 0 (DISCOVERY)                     ШАГ 3: КРИСТАЛЛИЗАЦИЯ SPEC
 ┌────────────────────────────────┐            ┌────────────────────────────────┐            ┌────────────────────────────────┐
 │ python install.py              │            │ Агент: /kb-research <идея>     │            │ Выбор стека зафиксирован:      │
 │ • Стек: Undecided (Idea-First) │            │ • Анализ платформ (ОС/GUI/CLI) │            │ • ADR-0001: Выбор стека/арх-ры │
 │ • Идея: "Кроссплатформенный..."│ ─────────> │ • Бенчмарки и лимиты           │ ─────────> │ • SPEC.md: Концепция + Архитектура
 │                                │            │ • Trade-off Matrix стеков      │            │ • README.md: Витрина проекта   │
 │ SPEC.md: status = discovery    │            │ • Отбраковка нежизнеспособных  │            │ • Roadmap.md: План Фазы 1      │
 └────────────────────────────────┘            └────────────────────────────────┘            └────────────────────────────────┘
```

### 2.2. Механика пресета `undecided` в `install.py`

В `STACK_PRESETS` добавляется нейтральный пресет:
```python
"undecided": {
    "name": "Undecided / Idea-First Research",
    "language": "TBD (Determined in Mode 0)",
    "file_ext": ".txt",
    "build_cmd": "echo 'No build command configured yet (run /kb-research)'",
    "test_cmd": "echo 'No test command configured yet (run /kb-research)'",
    "sample_contract": "# Архитектурный контракт будет определен по итогам RESEARCH-001\n",
    "bug_env": "  - ОС: TBD\n  - Стек: TBD (в процессе исследования)\n",
    "research_quirks": "<!-- Архитектурные ограничения и критерии выбора стека -->",
}
```

При этом:
1. В мастере `install.py` пункт меню:
   `5) Generic / Other Technology Stack`
   `6) 💡 Undecided / Idea-First (Стек будет определен агентом через /kb-research)`
2. Если указан флаг `--idea "<текст>"` или введен пресет `undecided`:
   - В `SPEC.md` раздел «1. Концепция и цели» сразу заполняется переданным описанием идеи.
   - В разделе «2. Архитектура и стек технологий» ставится явная отметка:
     `* **Статус стека:** Не определен. Требуется провести первичное исследование через команду агента: '/kb-research выбор-стека-и-архитектуры'.`
   - Приветственное резюме инсталлятора явно подсказывает первый шаг:
     `"Начните работу с команды: /kb-research <исследование идеи и выбор стека>"`!

## 3. Защита от дрифта документации: Инвариант Живой Спецификации (Living Spec)

### 3.1. Разделение зон ответственности корневых документов

| Документ | Роль | Когда обновляется | Чего НЕ должно быть |
| :--- | :--- | :--- | :--- |
| **`SPEC.md`** | **Мастер-Спецификация (Ground Truth):** архитектура системы, ключевые модули, внешние контракты и текущие возможности. | При изменении архитектуры, добавлении модулей, на границе фаз (`/kb-release`). | Исторических логов сессий (для этого есть `Devlog.md`). |
| **`README.md`** | **Витрина проекта (Public Storefront):** для кого проект, быстрый старт, установка, примеры использования и ссылки на документацию. | При изменении CLI-команд, флагов, требований к окружению или релизе фаз. | Внутренних деталей реализации отдельных функций. |
| **`Devlog.md`** | **Хроника разработки (Append-Only Journal):** даты сессий, решенные задачи, баги, замеры производительности. | В конце каждого таска или сессии разработки. | Полных спецификаций модулей. |

### 3.2. Точки контроля Living Spec в жизненном цикле

1. **Точка А: Завершение таска (`/kb-complete`):**
   Если выполненная задача имеет модификатор типа `feat` или `arch` и изменяет публичные интерфейсы (новые флаги CLI, новые модули ядра), чеклист `kb-complete` дополняется шагом:
   `- [ ] Актуализировать SPEC.md / README.md, если задача изменила публичный интерфейс или системную архитектуру.`
2. **Точка Б: Релиз фазы (`/kb-release`):**
   Релиз фазы — это официальная фиксация стабильного состояния продукта. В префлайт-чеки `kb-release` добавляется обязательная проверка:
   - Проверен ли `README.md` на актуальность примеров CLI / API?
   - Отражает ли `SPEC.md` фактическое состояние архитектуры на момент релиза `vX.Y.Z`?
3. **Точка В: Эвристический аудит в `kb_lint.py`:**
   Линтер проверяет разницу между актуальной датой фазы в `Roadmap.md` и полем `updated` в `SPEC.md`. Если разрыв превышает 2 закрытые фазы, линтер выводит неблокирующее предупреждение:
   `WARN: SPEC.md was not updated since Phase 1, but Phase 3 is completed. Consider syncing Master Spec.`

## 4. Сравнительный анализ альтернатив (Trade-off Matrix)

| Критерий | 1. Статус-кво (жесткий стек, статичный SPEC) | 2. Полная автогенерация SPEC из кода | 3. Пресет Idea-First + Living Spec чеки (Выбранный) |
| :--- | :--- | :--- | :--- |
| **Удобство старта с нуля (Greenfield)** | 🔴 Низкое (надо угадывать стек) | 🔴 Неприменимо (кода еще нет) | 🟢 Идеальное (фокус на идее) |
| **Точность `SPEC.md` на фазах 5+** | 🔴 Ужасная (полный дрифт) | 🟡 Зависит от генератора (без концепции) | 🟢 Высокая (актуальный Ground Truth) |
| **Нагрузка на разработчика** | 🟢 Нулевая (документы гниют сами) | 🟡 Требует настройки тулинга | 🟢 Минимальная (простые чеки в релизе) |
| **Соответствие философии Docs-as-Code**| 🔴 Нарушает (спецификация врет) | 🟡 Документация вторична по отношению к коду | 🟢 100% соответствие (Spec drives code) |

## 5. Отвергнутые варианты (Rejected Alternatives)

* ❌ **Генерация `SPEC.md` исключительно постфактум из кода через AST-парсеры:**  
  *Причина отказа:* Нарушает фундаментальный принцип Docs-as-Code и Clean Architecture. Спецификация задает намерения, границы и требования, а не просто документирует уже написанный код.
* ❌ **Блокирующая ошибка в `kb_lint.py`, если `SPEC.md` не менялся в коммите:**  
  *Причина отказа:* Чрезмерная тирания тулинга (Hostile DX). Мелкие багфиксы и рефакторинги не должны требовать правок мастер-спецификации. Контроль должен быть предупреждающим (Warning / Pre-flight check в релизе).
