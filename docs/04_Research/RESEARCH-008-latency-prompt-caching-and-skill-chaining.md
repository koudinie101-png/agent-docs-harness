## 1. Контекст, проблема и проверяемые гипотезы

### 1.1. Контекст
После реализации Фазы 5 (High-SNR оптимизация токенов, сжатие монолита `docs-as-code` в легкий роутер, введение Anti-Echo протокола) поступила экспертная гипотеза о причинах наблюдаемого роста задержки отклика (latency) агента в среде Antigravity.

Ключевые утверждения критики:
1. **Деградация Prompt Cache (Cache Trashing):** Динамическая догрузка скиллов ломает статический префикс системного промпта, вызывая постоянный Cache Miss и полный перерасчет prefill на стороне LLM-сервера.
2. **Двойной сетевой round-trip (Tool Chaining):** Вместо прямого ответа агент тратит промежуточный шаг на вызов `view_file` для чтения `SKILL.md`, удваивая время ожидания первого полезного токена (TTFT).
3. **Парадокс Anti-Echo и Reasoning:** Сжатие ответа до 3–5 пунктов требует интенсивного reasoning-анализа модели, что медленнее потокового вывода прямого копирования кода (dump).

### 1.2. Проверяемые гипотезы
* **Гипотеза 1 (Стабильность системного префикса в Antigravity):** В среде Antigravity системный префикс промпта не мутирует при вызове скиллов. Реестр `<skills>` статичен, а тело скилла попадает в хвост диалога как `tool_result`, поэтому KV-кэш префикса не инвалидируется.
* **Гипотеза 2 (Фактор Chaining как главный драйвер задержки):** Главная причина субъективной задержки — скрытый двухтактный вызов инструмента (`view_file` на `SKILL.md`), обусловленный системной инструкцией среды: `you MUST read its SKILL.md instructions using view_file before proceeding`.
* **Гипотеза 3 (Trade-off: Round-trip Latency vs Attention Degradation):** Попытка вернуть монолит на 40 КБ в префикс устранит один round-trip, но вернет проблемы 30-шаговых сессий: "Lost in the Middle", сбои следования инвариантам (No-Code в Режиме 1) и квадратичный рост затрат на внимание на длинных контекстах.
* **Гипотеза 4 (Решение Zero Round-Trip Dispatch):** Размещение фундаментальных процедурных инвариантов 4 режимов непосредственно в Always-On файле `AGENTS.md` позволяет агенту формировать ответ мгновенно без обязательного чтения вспомогательного `SKILL.md` на типовых командах.

## 2. Анализ архитектуры инференса Antigravity и Prompt Caching

### 2.1. Структура промпта и механика кэширования префикса

В Antigravity сборка контекста выполняется в строго детерминированном порядке:

```
[Статический системный префикс (KV-Cache Hit)]
├── 1. Identity & Environment Metadata
├── 2. User Information & Paths
├── 3. User Rules (Global + Workspace AGENTS.md)
├── 4. Static Skills Registry (<skills>: Name + Path + Description)
├── 5. Subagents & Messaging Protocols
├── 6. Tools Declarations
└── 7. Guidelines & Communication Style
                    ▼
[Динамический контекст диалога (Append-Only)]
├── User Message: "/kb-plan feature-x"
├── Model: Tool Call `view_file(path/to/SKILL.md)`  <── ТАКТ 1 (Round-trip 1)
├── Tool Result: [Содержимое SKILL.md]
└── Model: "План фичи..."                            <── ТАКТ 2 (Round-trip 2)
```

**Вывод по Гипотезе 1:**  
Критика о «поломке статического префикса из-за динамической подгрузки скиллов» **технически несостоятельна в архитектуре Antigravity**. Префикс `<skills>` содержит лишь легковесный каталог (`name` + `description`), который остается неизменным. Содержимое скилла добавляется в конец истории сообщений как результат работы инструмента `view_file`. Префиксный кэш сервера (Gemini / Anthropic) остается «горячим» (Cache Hit).

### 2.2. Анатомия задержки: где реально теряются секунды?

| Этап | Механика | Задержка (сек) | Примечание |
| :--- | :--- | :--- | :--- |
| **Такт 1: Анализ намерения** | LLM генерирует tool call `view_file(SKILL.md)` | **1.5 – 3.5 с** | Сетевой round-trip 1 + генерация tool_call |
| **Клиентский I/O** | Antigravity читает файл с SSD | **0.01 – 0.05 с** | Пренебрежимо мало |
| **Такт 2: Префилл + Рассуждение** | LLM считывает `tool_result`, думает (Reasoning) | **2.0 – 5.0 с** | Сетевой round-trip 2 + reasoning tokens |
| **Генерация ответа** | Стриминг текста в интерфейс | **1.0 – 2.5 с** | Стриминг ответа |
| **ИТОГО задержка** | Двухтактная схема (Chaining) | **4.5 – 11.0 с** | **Субъективное ощущение зависания** |

Если бы агент мог ответить сразу на основе Always-On правил в `AGENTS.md` (однотактная схема):
* **ИТОГО задержка без Chaining:** **1.8 – 4.0 с** (сокращение времени ожидания в 2.5–3 раза!).

## 3. Анализ компромиссов (Trade-off Matrix)

| Подход | Round-trips на команду | Нагрузка на KV-кэш | Риск Lost-in-the-Middle | Устойчивость на 30 шагах |
| :--- | :--- | :--- | :--- | :--- |
| **1. Монолит в системном промпте (Статус-кво до Фазы 5)** | 1 такт (быстро) | 🔴 Очень высокая (+40 КБ Always-On) | 🔴 Высокий (размывание внимания) | 🔴 Быстрое переполнение лимитов |
| **2. Чистый On-Demand роутер (Фаза 5)** | 2 такта (медленно) | 🟢 Минимальная (+17 КБ статики) | 🟢 Нулевой (высокая плотность) | 🟢 Идеальная (чистая история) |
| **3. Гибридный Hot-Invariants Dispatch (Рекомендуемый)** | **1 такт (быстро)** | 🟢 Оптимальная (+19 КБ статики) | 🟢 Минимальный | 🟢 Идеальная |

## 4. Отвергнутые варианты (Rejected Alternatives)

* ❌ **Возврат к монолиту всех скиллов в одном файле на 40+ КБ:**  
  *Причина отказа:* Устранение одного round-trip ценой загрязнения всего окна контекста приводит к деградации внимания на длинных сессиях и росту затрат на каждый токен внимания.
* ❌ **Отказ от протокола Anti-Echo ради «быстрого копирования кода»:**  
  *Причина отказа:* Печатание сотен строк кода в чат засоряет историю сессии за 3–4 шага, превращая контекст в нечитаемую простыню. Экономия миллисекунд на reasoning оборачивается падением качества кода на следующих шагах.

## 5. Выводы и практические рекомендации

1. **Экспертная оценка отзыва:**  
   Критика абсолютно точна в определении **симптома** (рост воспринимаемой задержки) и роли **двухтактного вызова (Tool Chaining)**. Однако объяснение через «Cache Trashing статического префикса» ошибочно в силу архитектуры Antigravity.
2. **Как ускорить работу без потери High-SNR:**
   * **Шаг 1 (Hot Invariants в `AGENTS.md`):** Мы уже зафиксировали канонический 4-этапный жизненный цикл (Режим 0 Discovery, Режимы 1–3 Delivery) прямо в `AGENTS.md`. Поскольку `AGENTS.md` всегда загружен в горячий контекст, агенту **не обязательно вызывать `view_file` для чтения `SKILL.md`**, если команда тривиальна и понятна из контекста.
   * **Шаг 2 (Параллелизация I/O при необходимости скилла):** Если агенту требуется догрузить `SKILL.md`, он должен в этом же первом такте запрашивать сопутствующие файлы контекста (например, `Roadmap.md` или `Kanban.md`), исключая возникновение 3-го и 4-го тактов.
   * **Шаг 3 (Моделирование режима рассуждений):** Для быстрых команд переключаться на модели с низким latency prefill (например, Gemini Flash), а для сложных архитектурных исследований Режима 0 — осознанно использовать Thinking-модели, где пауза на reasoning является необходимой платой за глубину анализа.
