## 1. Проблема и контекст исследования

### 1.1. Контекст
Современные AI-агенты вышли за рамки чистой бэкенд- и алгоритмической разработки. Агенты активно верстают экраны (SwiftUI, Jetpack Compose, WinUI, React, Tailwind, Textual/TUI), генерируют визуальные стили, проектируют многопользовательские и распределенные сценарии.

При этом исторический стандарт Docs-as-Code в `agent-docs-harness` оптимизировался преимущественно под кодовые интерфейсы и бэкенд-сервисы (контракты интерфейсов, модульные юнит-тесты, терминальные CLI-команды).

### 1.2. Проблематика
1. **«Слепая разработка» интерфейсов (Blind UI Coding):**  
   Без явных визуальных требований агент генерирует разметку исключительно по текстовым эвристикам, забывая состояния экранов (`Empty`, `Loading`, `Error`), краевые случаи адаптивности (Safe Areas, темная/светлая тема, клавиатурный фокус) и доступности (a11y).
2. **Хаос и раздувание репозитория бинарниками (Git Bloat & Vault Clutter):**  
   Если агент сохраняет скриншоты и макеты бессистемно, репозиторий за несколько итераций раздувается сотнями мегабайт бинарных диффов. В Obsidian неструктурированные вложения замусоривают корневой граф знаний.
3. **Вызов гетерогенных систем (Heterogeneous Multi-Target & Companion Systems):**  
   Значительная доля современных систем не является монолитом под одну ОС. Системы связывают разнородные узлы:
   - `Windows + Android` (companion-утилиты, синхронизация телефона и ноутбука);
   - `macOS + iOS` (экосистемные приложения, Continuity, BLE/AirDrop);
   - `Windows + iOS` (кроссплатформенные сопутствующие клиенты);
   - `Linux + Android` (IoT-шлюзы, мобильное управление);
   - `Web + Mobile + Desktop` (мультиплатформенные клиенты с общим бэкендом).
   Харнесс категорически **не должен жестко хардкодить имена конкретных ОС**, сохраняя гибкость, расширяемость и принцип **Zero Dependencies (чистый Python 3 stdlib)**.

### 1.3. Проверяемые гипотезы
* **Гипотеза 1 (Универсальная композитная абстракция):** Представление платформ в виде композитного списка узлов (`--ui <target1,target2>`) позволяет без усложнения ядра масштабироваться от чистых headless-сервисов до распределенных companion-комплексов из $N$ платформ.
* **Гипотеза 2 (Изоляция постоянных и эфемерных ассетов):** Разделение хранения постоянных пруфов задач (`docs/assets/screenshots/TASK-XXX.png`) и временных E2E-диффов (`tmp/ui_snapshots/` в `.gitignore`) полностью снимает риск раздувания Git-репозитория.
* **Гипотеза 3 (Obsidian DX & авто-роутинг вложений):** Конфигурация `docs/.obsidian/app.json` (`"attachmentFolderPath": "assets/screenshots"`) обеспечивает идеальный DX вставки скриншотов по `Ctrl+V` без ручного перемещения файлов.
* **Гипотеза 4 (Модульная токен-экономика High-SNR):** Разделение архитектуры на единый транспортный протокол (`01_Architecture/Protocols/`) и изолированные платформенные спецификации (`01_Architecture/Targets/<Platform>.md`) экономит 60–70% контекста LLM, так как агент читает только узел текущей задачи.
* **Гипотеза 5 (Механический контроль линтера Tier 1):** Индексация медиафайлов в `file_map` скрипта `kb_lint.py` с очисткой пайпов размера (`![[image.png|600]]`) и контролем веса ($\le 2\text{ MB}$) гарантирует отсутствие битых ссылок и тяжелых файлов в релизных сборках.

## 2. Анализ механизмов и стресс-тестирование

### 2.1. Концепция: «Heterogeneous Target Nodes» (Гетерогенные узлы)

Вместо жестких констант архитектура вводит 3 ортогональные плоскости:

```text
┌─────────────────────────────────────────────────────────────┐
│                 Interaction Bus / Protocol                  │
│       docs/01_Architecture/Protocols/ (SSOT Контракт)       │
└──────────────┬───────────────────────────────┬──────────────┘
               │                               │
               ▼                               ▼
┌─────────────────────────────┐ ┌─────────────────────────────┐
│       Target Node A         │ │        Target Node B        │
│   (напр. Desktop Windows)   │ │    (напр. Mobile Android)   │
│ docs/01_Architecture/       │ │ docs/01_Architecture/       │
│ Targets/Windows.md          │ │ Targets/Android.md          │
└──────────────┬──────────────┘ └──────────────┬──────────────┘
               │                               │
               ▼                               ▼
┌─────────────────────────────────────────────────────────────┐
│                 Semantic Design System                      │
│        docs/01_Architecture/UI_Design_System.md             │
│    (Семантические токены -> Маппинг на HIG / M3 / Fluent)   │
└─────────────────────────────────────────────────────────────┘
```

1. **Protocol SSOT:** Независимое от языка и ОС описание протокола взаимодействия, форматов сообщений (JSON, Protobuf, байтовые структуры) и стейт-машины сопряжения.
2. **Target Node Spec:** Платформенные особенности (фоновое выполнение, энергопотребление, Doze Mode, Scoped Storage, права брандмауэра, системный трей).
3. **Semantic Tokens:** Абстрактные токены интерфейса (`Color.Brand`, `Spacing.Card`, `Action.Primary`), которые на уровне кода маппируются на нативные рекомендации целевой ОС (Microsoft Fluent, Apple HIG, Google Material 3, Web CSS).

### 2.2. Стресс-тестирование структуры хранения ассетов

Были исследованы три модели размещения визуальных файлов:

| Модель хранения | Организация | Плюсы | Минусы и риски | Вердикт |
| :--- | :--- | :--- | :--- | :--- |
| **A. Локально рядом с задачей** | `docs/02_Tasks/Specs/.../img/` | Ассеты лежат рядом со спецификацией | Хаос путей, дублирование общих картинок, поломка Obsidian `Ctrl+V` (разбрасывает по корню) | Отклонена |
| **B. Внешний облачный хостинг** | Внешние URL (S3, Figma, Imgur) | Репозиторий легкий | Нарушение автономности (Off-grid), риск Link Rot, невозможность работы локально в Obsidian | Отклонена |
| **C. Единое изолированное хранилище `docs/assets/`** | `docs/assets/{mockups,screenshots}/<target>/` | Автономия базы знаний, нативная работа с `app.json`, четкая изоляция | Требуется контроль веса файлов в линтере | **Рекомендована** |

### 2.3. Механика предотвращения Git Bloat

```text
Скриншоты и визуальные ассеты
  ├── Постоянные проектные пруфы (Permanent Artifacts):
  │     docs/assets/screenshots/<target>/TASK-XXX.png  ==> Фиксируются в Git (Лимит <= 2 MB)
  │     docs/assets/mockups/flows/FLOW-YYY.png        ==> Фиксируются в Git
  │
  └── Временные прогоны автотестов (Ephemeral Diff Artifacts):
        tmp/ui_snapshots/**                           ==> Заблокированы в .gitignore
```

## 3. Практические замеры и спецификация интеграции

### 3.1. Параметризация CLI и инсталлятора `install.py`

Параметр `--ui` расширяется до поддержки композитного списка таргетов:
* Одиночные: `--ui web`, `--ui mobile`, `--ui desktop`, `--ui tui`, `--ui none`.
* Гетерогенные: `--ui windows,android`, `--ui macos,ios`, `--ui linux,android`, `--ui web,mobile`.
* Автодетект: сканирование маркеров проектов в поддиректориях (`apps/*`, `src/*`, `packages/*`).

#### Двухступенчатая активация (Single-Target vs Multi-Target):
* **При 1 узле (`--ui web`, `--ui desktop`, `--ui tui`):** создаются `docs/assets/`, конфигурация `app.json`, спецификация `UI_Design_System.md` и внедряется матрица 4 состояний экрана. Избыточные каталоги протоколов и кросс-девайсных узлов не создаются.
* **При $\ge 2$ узлах (`--ui windows,android` и т.д.):** дополнительно создаются `01_Architecture/Protocols/`, изолированные спецификации `01_Architecture/Targets/<Node>.md`, каталог сквозных снимков `docs/assets/screenshots/multi-device/` и стейт-машина распределенного сопряжения.

#### Интеграция с Obsidian и защита настроек:
1. `docs/.obsidian/app.json`:
   ```json
   {
     "attachmentFolderPath": "assets/screenshots"
   }
   ```
2. **Исключение в `.gitignore`:** в функции `handle_gitignore()` инсталлятора добавляется правило `!.obsidian/app.json` (наравне с существующим `!.obsidian/graph.json`), чтобы Git отслеживал настройку вложений.
3. **Безопасный мерж при `--update`:** если `docs/.obsidian/app.json` уже существует, инсталлятор не перезаписывает файл целиком, а безопасно мержит ключ `"attachmentFolderPath": "assets/screenshots"`, сохраняя все пользовательские настройки Obsidian (темы, плагины).
4. **Сохранение лимита шаблонов (`test_16`):** стартовые файлы `UI_Design_System.md` и `Targets/<Node>.md` генерируются динамически через `create_starter_docs()` напрямую в `01_Architecture/`, не добавляя лишних `.md` в `docs/00_Templates/` и гарантируя сохранение жесткого лимита `00_Templates/ <= 28 KB`.

### 3.2. Матрица состояний экрана и Visual DoD для Headless/CLI сред

1. **The 4-State Matrix:** В Режиме 1 (`/kb-plan`) и Режиме 2 (`/kb-task`) вводится требование обязательного описания 4 состояний любого интерактивного представления:
   - **Empty State:** экран при отсутствии данных (первый запуск, нет сопряженных устройств, пустой список).
   - **Loading / Pending State:** состояние ожидания ответа узла/сети (спиннер, скелетон, прогресс передачи).
   - **Error State:** сбой транспорта, таймаут сопряжения, отказ в правах доступа, коллизия пакетов.
   - **Populated / Active State:** штатное отображение активных данных.
2. **Visual DoD для Headless / CLI сред:**  
   Если агент выполняет задачу в среде без дисплея/эмулятора (CI/CD контейнер, удаленный SSH, чистый CLI) и не может физически снять скриншот, он обязан сформировать ASCII/SVG-вайрфрейм или сгенерировать интерактивный предпросмотр (`generative_ui`), подготовив слот в отчете:  
   `![Скриншот](../../assets/screenshots/TASK-XXX.png) <!-- TODO: Вставьте скриншот через Ctrl+V в Obsidian -->`.  
   Это позволяет успешно завершить `/kb-complete` без зависания и ошибок окружения.

### 3.3. Матрица состояний кросс-платформенной связки
Для взаимодействия между узлами проектируется стейт-машина распределенной связки:
$$\text{DISCONNECTED} \xrightarrow{\text{Discovery}} \text{PAIRING (QR/PIN)} \xrightarrow{\text{Handshake}} \text{SYNCED} \xrightarrow{\text{Sleep/Background}} \text{SUSPENDED}$$

### 3.4. Адаптация линтера `kb_lint.py` и утилиты релизов `kb_release.py` (Tier 1)

1. **Индексация ассетов в `kb_lint.py` без коллизий:**
   - Список расширений: `{.png, .jpg, .jpeg, .webp, .svg, .gif, .canvas, .excalidraw}`.
   - **Критический инвариант:** медиафайлы индексируются в `file_map` **строго с расширением** (`f.name` и `f.name.lower()`), но **НЕ** по голому стему (`f.stem`). Это гарантирует, что скриншот `TASK-001.png` не затрет в словаре спецификацию `TASK-001.md`, ломая викиссылки `[[TASK-001]]`.
2. **Очистка синтаксиса размера в `kb_lint.py`:** регулярное выражение `parse_wikilinks` корректно отсекает параметры размера Obsidian: `![[image.png|600x400]]` $\to$ таргет `image.png`.
3. **Проверка стандартных изображений:** парсинг `!\[.*?\]\((.*?)\)` и проверка физического существования локальных относительных путей.
4. **Asset Weight Gate:** сканирование файлов внутри `docs/assets/` с выдачей `WARN`, если размер $> 2\text{ MB}$, с рекомендацией оптимизации в WebP/SVG.
5. **Адаптация `convert_wikilinks_to_github_markdown()` в `kb_release.py`:**
   - Предотвращение ошибочного дописывания `.md` к изображениям (например, исключение превращения `![[image.png]]` в `image.png.md`).
   - Корректная обработка пайпов размера (`|600`) при экспорте релизных заметок в GitHub Markdown.

## 4. Сравнительный анализ (Trade-off Matrix)

| Критерий | Вариант 1: Моно-стековый хардкод (только Windows+Android) | Вариант 2: Универсальные гетерогенные узлы (Предлагаемый) | Вариант 3: Полный отказ от UI-контура (только код) |
| :--- | :--- | :--- | :--- |
| **Гибкость комбинаций** | ❌ Низкая (только одна пара) | ✅ Неограниченная ($N$ любых платформ) | ❌ Отсутствует |
| **Zero-Dependencies** | ✅ Сохраняется (Python stdlib) | ✅ Сохраняется (Python stdlib) | ✅ Сохраняется |
| **Токен-эффективность LLM** | ⚠️ Средняя (лишние данные чужих ОС) | ✅ Высокая (модули `Targets/<Node>.md`) | ❌ Низкая (галлюцинации UI) |
| **Защита от Git Bloat** | ⚠️ Зависит от разработчика | ✅ Гарантирована (`.gitignore` + линтер) | ✅ Полная (нет ассетов) |
| **Поддержка Obsidian DX** | ⚠️ Ручная сортировка вложений | ✅ Автоматическая (`app.json`) | ❌ Нет поддержки |

## 5. Отвергнутые варианты во избежание повторных ошибок

1. ❌ **Жестко зашитые пары платформ в перечислениях Python (`Enum: WindowsAndroid, MacOsIos`):**  
   *Причина отказа:* Нарушает универсальность харнесса. Создание комбинаторного взрыва перечислений для всех возможных связок ОС и языков нежизнеспособно.
2. ❌ **Размещение скриншотов внутри папок задач (`02_Tasks/Specs/.../screenshots`):**  
   *Причина отказа:* Obsidian не поддерживает динамические папки вложений для каждого подкаталога без сторонних плагинов. `Ctrl+V` сбрасывал бы картинки в корень, порождая мусор.
3. ❌ **Хранение автоматических E2E-диффов в репозитории:**  
   *Причина отказа:* Ежедневные прогоны автотестов верстки раздувают `.git` на сотни мегабайт за пару месяцев. Все временные снимки обязаны изолироваться в `tmp/ui_snapshots/`.

## 6. Выводы и архитектурные правила

1. **Правило гетерогенной модульности:** Мультиплатформенный проект конфигурируется через композитный список узлов в ключе `--ui`. База знаний формирует изолированные модули в `01_Architecture/Targets/` и общий контракт шины в `01_Architecture/Protocols/`.
2. **Правило 4 состояний:** Любая UI-спецификация в Режиме 1 и 2 обязана документировать состояния `Empty`, `Loading`, `Error`, `Populated`.
3. **Правило изоляции ассетов:** Постоянные макеты и скриншоты хранятся в `docs/assets/`, временные автоснапшоты изолируются в `tmp/` через `.gitignore`. Линтер `kb_lint.py` осуществляет Tier 1 контроль ссылок на изображения и веса файлов.
4. **Связанное решение:** Принять выводы исследования в форме [[../03_Decisions_ADR/ADR-0026-heterogeneous-ui-ux-and-visual-asset-management|ADR-0026]] и включить в Дорожную карту разработки [[../02_Tasks/Roadmap|Roadmap.md]].
