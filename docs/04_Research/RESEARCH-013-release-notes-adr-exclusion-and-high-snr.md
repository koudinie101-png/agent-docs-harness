## 1. Проблема и гипотезы

При анализе релизных заметок для `v0.8.0` и `v0.7.0` на GitHub обнаружено избыточное раздувание описания:
В публичном чейнджлоге `dist/RELEASE_NOTES.md` под заголовком `### 🏛️ Архитектурные решения (ADR)` выводится массивный список из 14–16 ссылок на исторические ADR, начиная с самых первых дней проекта (`ADR-0001: Zero Dependencies`, `ADR-0002: Bundling` и т.д.).

### Проверяемые гипотезы:
1. **Гипотеза 1 (Смешение целевых аудиторий):** Публичные заметки о релизе на GitHub (`dist/RELEASE_NOTES.md`) ориентированы на *пользователей и интеграторов инструмента*, которым важна функциональность, инструкции обновления и целостность артефактов. Внутренние архитектурные компромиссы (ADR) предназначены для *мейнтейнеров и контрибьюторов* и должны жить в базе знаний, а не в теле релиза.
2. **Гипотеза 2 (Нарушение High-SNR стандарта):** Наличие длинного списка ADR размывает фокус, создает информационный шум (Low SNR) и противоречит принятому в проекте [[../03_Decisions_ADR/ADR-0009-high-snr-token-architecture-and-context-efficiency|ADR-0009]].
3. **Гипотеза 3 (Дефект кумулятивной агрегации):** В `scripts/kb_release.py` функция сбора данных сгребает все файлы со статусом `accepted` без фильтрации по дате или фазе релиза, что приводит к неограниченному $O(N)$ росту размера релизных заметок с каждым новым релизом.
4. **Гипотеза 4 (Оптимальный формат):** Исключение секции ADR из публичного шаблона `generate_public_release_notes()` снижает объем заметки на 35–45%, улучшает восприятие ключевых фич и полностью устраняет проблему кумулятивного шума.

## 2. Анализ индустриальных стандартов и лучших практик

### 2.1. Keep a Changelog (Индустриальный канон)
Спецификация [Keep a Changelog](https://keepachangelog.com/) определяет четкую структуру секций для каждого релиза:
- `Added` — новая функциональность.
- `Changed` — изменения в существующей функциональности.
- `Deprecated` — функционал, который будет удален в будущих версиях.
- `Removed` — удаленный функционал.
- `Fixed` — исправленные баги.
- `Security` — исправления уязвимостей.

*Вывод:* Ни один общепринятый стандарт оформления чейнджлогов не предусматривает отдельной секции для внутренних дизайн-документов или ADR.

### 2.2. Анализ ведущих Open-Source проектов на GitHub

| Проект | Структура Release Notes на GitHub | Отражение архитектурных решений |
| :--- | :--- | :--- |
| **Kubernetes** | `What's New`, `Urgent Upgrade Notes`, `Deprecations`, `Notable Features`, `Bug Fixes`. | Архитектурные KEP (Kubernetes Enhancement Proposals) упоминаются только инлайн в конкретных фичах: `Feature X graduated to GA (#12345, @author)`. Отдельной секции KEP нет. |
| **React** | `Highlights`, `New Features`, `Breaking Changes`, `Bug Fixes`. | RFC упоминаются ссылкой внутри описания крупного нововведения. Секции RFC нет. |
| **Rust / Cargo** | `Compatibility Notes`, `Language`, `Compiler`, `Libraries`, `Stabilized APIs`. | RFC фиксируются в commit message и трекерах, в релизных заметках фокус на доступных API. |
| **Fastlane / CocoaPods** | `New Features`, `Bug Fixes`, `Documentation`. | Сугубо утилитарный чейнджлог для разработчиков. |

### 2.3. Разделение зон ответственности в Docs-as-Code

```

│                       Docs-as-Code                          │
├──────────────────────────────┬──────────────────────────────┤
│    Внутренняя база знаний    │    Публичный чейнджлог       │

├──────────────────────────────┼──────────────────────────────┤

└──────────────────────────────┴──────────────────────────────┘
```

## 3. Практические замеры и метрики

### Замер объема релизных заметок v0.8.0

| Метрика | С секцией ADR (текущий вид) | Без секции ADR (целевой High-SNR вид) | Разница |
| :--- | :--- | :--- | :--- |
| **Объем текста (байты)** | 7 425 байт | 4 080 байт | **-45.1%** |
| **Количество строк** | 65 строк | 37 строк | **-43.1%** |
| **Количество токенов (LLM)** | ~1 650 токенов | ~910 токенов | **-44.8%** |
| **Ссылки на ADR** | 14 ссылок | 0 (или инлайн по необходимости) | **-100% шума** |
| **Высота первого экрана** | Секция ADR вытесняет таблицу SHA-256 за пределы экрана | Таблица SHA-256 и сниппет верификации видны без долгой прокрутки | **Высокий UX** |

## 4. Сравнительный анализ альтернатив (Trade-off Matrix)

| Вариант | Плюсы | Минусы и риски | Вердикт |
| :--- | :--- | :--- | :--- |
| **А. Кумулятивный список ADR (Текущее состояние)** | Видны все принятые решения проекта. | Огромный шум; $O(N)$ разрастание; смешение аудиторий; нарушение ADR-0009; вытеснение проверочных чексумм. | ❌ **Отклонён** |
| **Б. Фильтрация ADR строго по текущей фазе** | Устраняет кумулятивный рост. | ADR часто носят фундаментальный характер и не привязаны к одной фазе; публичному пользователю неинтересны внутренние нюансы реализации. | ❌ **Отклонён** |
| **В. Сворачивание под спойлер `<details>`** | Экономит визуальное место на экране. | Загромождает Markdown; всё ещё расходует токены в LLM-контексте; половинчатое решение. | ❌ **Отклонён** |
| **Г. Полное удаление секции ADR из публичных заметок + Инлайн-ссылки по необходимости (Рекомендуемый)** | 100% соответствие Keep a Changelog и High-SNR; компактность; моментальный доступ к Quick Install и SHA-256; максимальная плотность пользы. | Пользователи GitHub не видят список ADR (при необходимости могут перейти в `docs/03_Decisions_ADR`). | ✅ **Выбран** |

## 5. Отвергнутые варианты

1. **Оставить секцию ADR как есть:** Отклонено, так как это прямо противоречит философии проекта по устранению информационного мусора и приводит к захламлению релизов.
2. **Публиковать отдельный ADR-Changelog на GitHub:** Отклонено как оверинжиниринг, не несущий продуктовой ценности для конечного пользователя инсталлятора.

## 6. Выводы и правила стандарта

1. **Правило разделения контекста:**
   - Публичные Release Notes (`dist/RELEASE_NOTES.md` и тело GitHub Releases) содержат **ТОЛЬКО**:
     - Быстрый старт / Обновление (Quick Install / Upgrade)
     - Новые возможности (Features)
     - Исправленные дефекты (Bug Fixes)
     - Релизные артефакты и контрольные суммы SHA-256 (Artifacts & Checksums)
     - Ссылку на полный диф коммитов (Full Changelog)
   - Секция `### 🏛️ Архитектурные решения (ADR)` из публичных заметок **полностью исключается**.
2. **Связь с ADR через задачи (Инлайн-трассируемость):**
   - Если архитектурное решение критично для понимания фичи, ссылка на ADR дается инлайн в тексте задачи:
     ```markdown
     - [TASK-029](...): Пресет undecided и CLI-флаг --idea (архитектура: [ADR-0014](...)).
     ```
3. **Внутренние релизные документы (`docs/02_Tasks/Releases/`):**
   - Внутри архива базы знаний секция ADR сохраняется только в том случае, если в рамках фазы были приняты решения, но агрегация фильтруется строго по фазе (исключая кумулятивный дамп всех ADR проекта).
4. **Реализация:** Зафиксировать принятое решение в `ADR-0017` и зарегистрировать задачу на рефакторинг генератора заметок в `scripts/kb_release.py`.
