## 1. Контекст, вопрос и проверяемые гипотезы

### 1.1. Постановка вопроса

Пользовательский вопрос: **«Насколько crowded рынок решений со схожим функционалом и есть ли у нашего решения выгодная фича, способная выделить его на фоне других?»**

Вопрос распадается на три измеримые части:

1. **Плотность рынка:** сколько решений реально существует, а не сколько ссылок выдаёт поиск.
2. **Глубина пересечения:** какие именно функции пересекаются с нашим харнессом, а какие являются уникальными.
3. **Дифференциация:** какая фича (или комбинация) может быть рыночным клином, а какая — лишь паритетом.

### 1.2. Метод и границы исследования

* **Срез данных:** публичные README/документация ключевых проектов и GitHub API на **2026-10-18**. Звёзды GitHub — индикатор внимания, **не** качества и не размера рынка.
* **Что не делалось:** аудит исходного кода конкурентов, замеры производительности, интервью с пользователями, анализ выручки. Матрица отражает **заявленные** возможности публичной документации, а не фактическую реализацию.
* **Единица анализа:** фреймворк/инструмент, который задаёт процесс работы AI-агента в репозитории (research → plan → spec → code), а не отдельная библиотека, промпт или IDE.

### 1.3. Проверяемые гипотезы

| # | Гипотеза | Критерий фальсификации |
| :--- | :--- | :--- |
| **H1** | Категория «spec-driven / docs-as-code для AI» переполнена на уровне ключевых слов, но продуктового уровня достигают единицы | Если найдётся >20 активных проектов с >5k звёзд и полным жизненным циклом — гипотеза ложна |
| **H2** | Наши 4 режима, 16 шаблонов и 12 скиллов — не уникальная фича, а паритет | Если хотя бы 2 конкурента не покрывают plan/spec/tasks — гипотеза ложна |
| **H3** | Механическая проверка целостности базы знаний + барьер против автономного перевыполнения — редкая комбинация и потенциальный клин | Если у ≥2 конкурентов есть CI-линт базы знаний и Stop & Yield — гипотеза ложна |
| **H4** | Главный риск — не функциональность, а дистрибуция и порог входа | Если у проекта уже есть сопоставимая аудитория и демо — гипотеза ложна |

### 3.1. Что показывает матрица

1. **Средняя часть (plan → spec → tasks → code) полностью Commodity.** Здесь мы не отличаемся ничем; более того, у конкурентов больше сообщество, плагины и демо.
2. **Полный жизненный цикл research → release не покрывает никто, кроме нас.** Но «полнота» — это ширина, а не глубина: у конкурентов отдельные слои сделаны лучше.
3. **Две клетки действительно редки:** механический линт базы знаний и барьер против автономного перевыполнения. У OpenSpec/Backlog.md есть валидация артефактов/схем задач, но не линт ссылок, YAML, лимитов памяти, трассировки техдолга и топологии ассетов одновременно.
4. **Zero-deps и мульти-IDE — не дифференциатор.** Superpowers поддерживает 16 харнессов, OpenSpec — 30+, Spec Kit — десятки. Наши 7 адаптеров — паритет, а не преимущество.
5. **Obsidian-граф и визуальные ассеты — уникальны в выборке**, но это узкая аудитория и слабая готовность платить.

### 3.2. Честная оценка глубины

| Наша заявка | Статус | Комментарий |
| :--- | :--- | :--- |
| 4 режима | Паритет | Аналоги: brainstorm → plan → spec → implement у Superpowers/cc-sdd |
| 16 шаблонов | Паритет | Spec Kit/BMAD/OpenSpec поставляют сопоставимые шаблоны |
| 12 скиллов | Паритет | Superpowers и cc-sdd опережают по количеству и экосистеме |
| Zero-deps | Паритет/ниша | Cline MB тоже без зависимостей; ценность только для offline/enterprise |
| Stop & Yield | **Уникально** | Но копируется одной строкой в промпте; ценность сегментная |
| KB-линт | **Уникально** | Сложнее копировать: кодирует таксономию, ID, фазы, лимиты, топологию |
| Release + feedback + tech debt | **Редко** | Никто не bundl'ит это в один zero-dep инструмент |
| Rule compiler + golden tests | **Редко** | Инженерная гигиена; пользователю не видна, но снижает дрейф правил |

## 4. Сравнительный анализ позиционирования (Trade-off Matrix)

| Вариант | Плюсы | Минусы и риски | Вердикт |
| :--- | :--- | :--- | :--- |
| **A. Mass-market лёгкий SDD** (догнать OpenSpec/Spec Kit) | Понятная категория, быстрый онбординг | Опоздание, паритет, гиганты с маркетплейсами, нет дистрибуции | Отклонён |
| **B. Autonomy-first агентная ОС** (догнать Superpowers/cc-sdd) | Хайп, эффектные демо, автономные субагенты | Ресурсоёмко, противоречит ДНК Stop & Yield, гонка с 300k-звёздным лидером | Отклонён |
| **C. Governance/audit-слой для AI-репозиториев** (docs CI + evidence) | Использует уникальный линт и state machine; B2B/enterprise; интероперабелен | Уже рынок; нужны CI-интеграции и доказательства; «скучный» бренд | **Рекомендован** |
| **D. Obsidian-vault для агентных команд** | Уникальный UX, визуальный граф, ниша PKM | Слабая готовность платить, узкая аудитория | Только как wedge |

**Почему C:** сильнейшая сторона проекта — не «мы умеем планировать», а «мы умеем **доказывать**, что документация не сгнила». Это можно продать как комплаенс/аудит/надёжность, а не как очередной способ писать спеки. C также совместим с A и B: мы можем линтить чужие Spec Kit/OpenSpec/BMAD-артефакты, не заставляя менять процесс.

## 5. Отвергнутые варианты

* **Конкурировать количеством шаблонов и скиллов.** Это гонка, где выигрывает дистрибуция, а не качество; плюс прямой рост токен-бюджета (против [[../03_Decisions_ADR/ADR-0009-high-snr-token-architecture-and-context-efficiency|ADR-0009]]).
* **Собственный веб-дашборд/Kanban-UI.** Уже отклонён в [[../03_Decisions_ADR/ADR-0005-rejection-of-embedded-web-visualizer|ADR-0005]]; Backlog.md и spec-workflow-mcp закрывают эту нишу лучше.
* **PDF-отчёты и презентационные артефакты.** Отклонён в [[../03_Decisions_ADR/ADR-0006-rejection-of-standalone-pdf-report-generator|ADR-0006]]; не решает боль.
* **Полная автономия и субагент-оркестрация.** Противоречит [[../03_Decisions_ADR/ADR-0016-single-task-execution-barrier-and-stop-on-complete-protocol|ADR-0016]]; требует ресурсов, которых нет; рынок уже занят Superpowers.
* **«AI сам пишет всю документацию».** Убивает главную ценность — человеческий контроль и аудируемость; противоречит Human Guardrails.

## 6. Выводы и рекомендации

### 6.1. Ответ «сколько»

* **По ключевым словам:** тысячи (5 020 + 4 416 + 1 477 + 926 с пересечениями).
* **Продуктового уровня:** ~10–12 активных решений с аудиторией >5k звёзд.
* **Прямое пересечение жизненного цикла:** ~6–8.
* **Полный охват docs-governance (линт + релиз + фидбек + техдолг + память + барьер):** в выборке — только наш проект.

**Категория crowded, но не наша ниша.** Мы конкурируем не с «ещё одним SDD-фреймворком», а с отсутствием аудируемого контроля над документацией.

### 6.2. Есть ли выгодная фича

**Единой уникальной фичи нет.** Есть уникальная комбинация и один защищаемый механизм:

> **«Docs-as-Code с исполняемым контрактом»: база знаний — не папка Markdown, а артефакт, который проходит CI.**

`kb_lint.py` механически проверяет то, что конкуренты оставляют на дисциплину промпта: битые wikilinks, YAML, лимит процедурной памяти, трассировку `DEBT-XXX`, топологию ассетов, согласованность фаз, `research_basis`, семантику Devlog и висячие `TODO`. Это Tier 1-барьер, а не «напоминание в промпте» ([[../03_Decisions_ADR/ADR-0025-self-improving-defect-loop-and-quality-gates|ADR-0025]]).

**Вторая ставка — контринтуитивная:** **containment вместо автономии** (Stop & Yield + Single-Task Barrier). Пока рынок соревнуется в том, кто дольше проработает без человека, мы продаём предсказуемость и остановку. Это не массовый вкус, но сильный аргумент для regulated/enterprise/audit-сегмента.

**Что не является дифференциатором:** 4 режима, 16 шаблонов, 12 скиллов, zero-deps, 7 адаптеров, Obsidian-граф. Это либо паритет, либо ниша.

### 6.3. Риски и ограничения

1. **Церемония против рынка.** OpenSpec прямо позиционируется как «легче и без жёстких гейтов»; наш харнесс тяжёлый. Массовый вайбкодер выберет скорость.
2. **Дистрибуция — главный дефицит.** 0 звёзд, 0 форков, нет LICENSE-файла (GitHub API не определяет лицензию), нет topics/homepage/демо. Лучшая фича не помогает без аудитории.
3. **Порог входа.** README на 367 строк и 12 скиллов — высокий когнитивный барьер; у лидеров вход — одна команда и 30-секундное демо.
4. **Копируемость.** Линт-правила можно воспроизвести; ров — таксономия + rule compiler + golden tests + накопленные инварианты, но он средний, не глубокий.
5. **Риск «швейцарского ножа».** Полный охват легко читается как «всё и ничего»; нужна одна острая история.

### 6.4. Рекомендуемые действия (не реализованы в этом исследовании)

1. **Перепозиционировать:** не «yet another SDD», а **«governance/audit layer for AI-written repos»**; слоган — «документация, которая падает в CI, когда гниёт».
2. **Вынести линт в самостоятельный клин:** GitHub Action, pre-commit hook, `--fix`, SARIF/Code Scanning; возможность линтить чужие Spec Kit/OpenSpec/BMAD-артефакты без смены процесса.
3. **Сделать 30-секундное демо в README:** агент пытается править код в Mode 1 → получает redirect; битая ссылка/просроченный техдолг → CI red; открытый `release_blocker` → релиз остановлен.
4. **Опубликовать замер (≥3 прогона):** токен-оверхед, доля пойманного дрейфа, время до первой задачи — против 2–3 конкурентов. Без цифр «мы строже» — лозунг.
5. **Закрыть adoption-блокеры:** файл `LICENSE`, topics, homepage, короткий quickstart, ссылка на демо.
6. **Целевые сегменты:** regulated/enterprise, долгоживущий brownfield, русскоязычные команды, offline/on-prem, мульти-агентные команды.
