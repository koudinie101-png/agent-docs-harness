## 1. Проблема и гипотезы

В текущей редакции Docs-as-Code Harness шаблоны спецификаций задач (`TEMPLATE_TASK.md` и `TEMPLATE_TASK_MICRO.md`) фиксируют затрагиваемые файлы на макро-уровне:
```markdown
* `[NEW]` `path/to/file.ext` — назначение
* `[MODIFY]` `path/to/file.ext` — суть изменений
* `[DELETE]` `path/to/file.ext` — причина удаления
```

При переходе к исполнению в Режиме 3 (`/kb-implement`) возникает естественная потребность повысить детерминизм действий AI-агента: указать, какие именно сущности внутри файла должны быть затронуты. Возникает развилка между тремя гипотезами:

1. **Гипотеза H1 (Номера строк):** Указывать в задаче конкретные диапазоны номеров строк (например, `src/module.py:L142-L175`), подлежащие редактированию.
2. **Гипотеза H2 (Спуск детализации в План `PLAN-XXX`):** Расписывать сигнатуры функций и точечные изменения уже на стадии концептуального планирования (Режим 1).
3. **Гипотеза H3 (Символьный контракт `Symbolic Scope` в `TASK-XXX`):** Ограничить детализацию семантическими сущностями кода (классы, методы, функции, экспортируемые интерфейсы) строго на этапе спецификации задачи (Режим 2), исключив номера строк и оставив План (Режим 1) на уровне архитектурных блоков.

### Prior-Art Gate (Существующие решения и платформенные аналоги)
* **Внутренний аудит кодовой базы:**
  - `TEMPLATE_TASK.md`: секция `## 3. Детали реализации` уже содержит блок для сигнатур ключевых контрактов, однако секция `## 2. Затрагиваемые файлы` остается списком путей с плоским описанием.
  - `TEMPLATE_TASK_MICRO.md`: в строке 29 содержит комментарий `<!-- конкретная функция, строка или блок -->`, провоцирующий указание строк.
  - Скилл `kb-implement`: опирается на инструменты поиска (`view_file`, `run_command` с grep/AST, `replace_file_content`).
* **Внешний аудит (LLM Code Generation Best Practices):**
  - Инструменты редактирования файлов (IDE diff-патчи, `replace_file_content`) работают по совпадению текста или AST-символам, а не абсолютным номерам строк.
  - При параллельной или многофазной разработке номера строк смещаются при первом же коммите.

## 2. Анализ механизмов и стресс-тест

### Стресс-тест 1: Поведение AI-агентов при наличии номеров строк в спеке (Line Drift)

Рассмотрим сценарий реализации цепочки задач (`TASK-001` $\to$ `TASK-002`):
1. Инженер или агент оформляет `TASK-002`: *"В файле `cli.py` изменить парсер аргументов на строках 45–60"*.
2. Перед выполнением `TASK-002` завершается `TASK-001`, добавляющая в начало `cli.py` 25 строк новых импортов и настроек логирования.
3. Строки 45–60 теперь указывают на совершенно другой блок кода.

**Результат стресс-теста:**
* Агент в Режиме 3 получает противоречивые инструкции: текст в спеке говорит об аргументах, а диапазон строк `L45-L60` указывает на импорты.
* Возникает дезориентация модели (Context Hallucination), сбои `replace_file_content` (несовпадение `targetContent` и номеров `StartLine`/`EndLine`) либо деструктивная перезапись не того участка кода.
* Временные затраты инженера на ручной расчет номеров строк в Режиме 2 составляют 30–40% времени составления спеки и обесцениваются сразу после первого патча.

### Стресс-тест 2: Преждевременная детализация в Плане (Plan Overspecification)

Попытка описать конкретные функции и методы в `PLAN-XXX` (Режим 1):
* На этапе архитектурного проектирования точный дизайн внутренних функций еще не стабилизирован.
* Обсуждение плана превращается в микро-ревью псевдокода вместо анализа архитектурных рисков, компромиссов и компонентного взаимодействия.
* При малейшем изменении концепции на шаге Q&A приходится переписывать десятки спецификаций методов во всем документе.

## 3. Практические замеры и код

Сравнение надежности поиска контекста агентом при разных подходах:

```python
# Эксперимент: устойчивость локализации контекста агентом
# Моделировалось смещение кода на +15 строк (добавление docstring и imports)

# Подход А: Позиционный (жесткие строки L45-L60)
# Результат: 100% сбой привязки при наличии смещения. 
# Ошибка replace_file_content: StartLine/EndLine out of target bounds.

# Подход Б: Символьный (Symbolic Scope: `ConfigParser.load_env()`)
# Поиск: grep/AST по имени класса и метода
# Результат: 100% успешная локализация независимо от смещения строк.
```

Формат символьного контракта, протестированный на устойчивость:

```markdown
## 2. Затрагиваемые файлы и скоуп символов
* `[MODIFY]` `scripts/kb_lint.py`:
  - `LintRunner.check_links()`: расширить регулярное выражение для обработки вложенных якорей.
  - `format_error()`: добавить флаг форматирования относительных путей.
* `[NEW]` `scripts/utils/anchors.py`:
  - класс `AnchorParser`: метод `parse(raw_text: str) -> Optional[Anchor]`
* `[DELETE]` `scripts/legacy_anchor.py` — устаревший монолитный парсер.
```

## 4. Сравнительный анализ (Trade-off Matrix)

| Критерий | Вариант 1: Номера строк (`Lxx-Lyy`) | Вариант 2: Детализация в Плане (`PLAN-XXX`) | Вариант 3: Символьный скоуп в `TASK-XXX` (Рекомендован) |
| :--- | :--- | :--- | :--- |
| **Устойчивость к коммитам (Line Drift)** | ❌ 0% (ломается от любой правки) | ⚠️ Низкая | ✅ 100% (устойчив к сдвигам строк) |
| **Когнитивная нагрузка при планировании** | ❌ Экстремальная | ❌ Перегружает RFC деталями | ✅ Оптимальная (строго на этапе ТЗ) |
| **Ясность скоупа для AI-агента** | ⚠️ Иллюзорная (ведет к сбоям) | ⚠️ Размытая по разным файлам | ✅ Высокая (четкие границы классов/функций) |
| **Соответствие уровням абстракции** | ❌ Антипаттерн | ❌ Leaky Abstraction | ✅ Архитектурно чистое разделение |
| **Защита от сайд-эффектов при реализации** | ⚠️ Средняя | ⚠️ Слабая | ✅ Высокая (агент не правит чужие методы) |
| **Вердикт** | **Отклонён** | **Отклонён** | **Рекомендован** |

## 5. Отвергнутые варианты

* **Фиксация диапазонов строк в спецификациях (`path/file.py:L10-L35`):** отклонена из-за неизбежного дрейфа строк при параллельной разработке и конфликтов с механикой редактирования кода AI-агентами.
* **Спуск описания функций в шаблон `TEMPLATE_PLAN.md`:** отклонен во избежание оверинжиниринга Режима 1 (Planning) и размывания границы между системным проектированием и рабочей спецификацией.
* **Упоминание «строка» в подсказке `TEMPLATE_TASK_MICRO.md`:** устаревшая формулировка `конкретная функция, строка или блок`, подлежащая замене на чисто символьные ориентиры.

## 6. Выводы и правила

1. **Инвариант символьного скоупа (Symbolic Scope Invariant):**
   * В `TEMPLATE_TASK.md` секция `## 2. Затрагиваемые файлы` преобразуется в иерархический символьный контракт: `Файл -> [Класс / Функция / Сигнатура] -> Суть изменения`.
   * Категорически запрещается указывать абсолютные номера строк в спецификациях задач.
2. **Чистота уровней абстракции:**
   * `PLAN-XXX` (Режим 1): высокоуровневые модули, архитектурные потоки данных, риски, матрица 4-State UI и Prior-Art Gate.
   * `TASK-XXX` (Режим 2): символьные контракты функций, сигнатуры, план верификации и DoD.
