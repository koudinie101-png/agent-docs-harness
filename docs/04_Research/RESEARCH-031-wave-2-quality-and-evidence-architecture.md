## 1. Проблема и гипотезы

### 1.1. Контекст проблемы
В рамках реализации инициатив **Волны 1 (Docs Integrity Gate)** харнесс получил непрерывный CI-контроль (Фазы 27–28), детерминированную навигацию и граф зависимостей `depends_on` (Фаза 30, `kb_state.py`), а также безопасный хирургический автофикс `kb_lint --fix` (Фаза 31). Это заложило прочный фундамент целостности базы знаний.

Однако аудит качества выполнения задач AI-агентами ([[RESEARCH-027-competitor-best-practices-and-adoption-backlog|RESEARCH-027]]) выявил системные проблемы следующего эшелона — на стыке формирования спецификации (Режим 2), проверки полноты реализации (Режим 3) и релизного экспорта:

1. **«Синдром уверенного угадывания» (Speculative Hallucinations):** При наличии неполных или противоречивых требований агент в Режиме 2 (`/kb-task`) склонен додумывать логику, придумывать несуществующие API и создавать видимость идеального ТЗ. Ошибки проектирования всплывают только на этапе эксплуатации.
2. **Иллюзия тестируемости (Shallow Verification):** ТЗ содержит словесные acceptance-критерии, но в коде агент реализует лишь один тривиальный «зеленый сценарий» (happy path), игнорируя краевые случаи и обработку ошибок. В базе знаний отсутствует механическая связь между конкретным требованием и проверяющим его тестом.
3. **Отсутствие доказанного ревью (Unguarded Convergence):** Прохождение тестов показывает лишь отсутствие фатальных исключений, но не гарантирует соответствие исходному скоупу. Агенты нередко меняют посторонние файлы, искажают контракты или срезают углы в архитектуре без формального подтверждения (Evidence).
4. **Дрейф при доработке существующего кода (Brownfield Drift):** ТЗ для существующих систем описываются монолитно, без разделения на добавленное, измененное и удаленное (`ADDED/MODIFIED/REMOVED`), что затрудняет инкрементальное обновление Master Spec (`SPEC.md`).
5. **Ручной шум в релизных записках:** Стандарт ADR-0034 зафиксировал необходимость разделения пользовательской выжимки и сворачиваемого технического аудита, но генерация в `scripts/kb_release.py` все еще выводит плоский список задач, требуя ручной постобработки.

### 1.2. Prior-Art Gate (Анализ ведущих агентных систем)
* **Spec Kit (GitHub / Anthropic):**
  - Внедрил концепцию маркеров `[NEEDS CLARIFICATION: ...]` — агент обязан явно маркировать пробелы в требованиях вместо попыток угадать намерение разработчика.
  - Использует строгие фазовые чек-листы качества спецификации («Phase -1 Spec Gate»).
* **OpenSpec (`anvil` schema):**
  - Ведет реестр `Scenario → Test Ledger`, где каждый пользовательский сценарий отображается на конкретный тестовый метод с жесткой проверкой покрытия.
  - Применяет формализм дельт (`ADDED`, `MODIFIED`, `REMOVED`) для описания изменений в brownfield-репозиториях.
* **Superpowers & cc-sdd:**
  - Ввели двухстадийное ревью: Stage 1 (Spec Compliance: проверка соответствия ТЗ, символов и DoD) $\to$ Stage 2 (Code Quality: архитектура, безопасность, чистота кода).
  - Сверка сходимости (Convergence): сопоставление фактического `git diff` с заявленным в ТЗ скоупом файлов.

### 1.3. Гипотезы исследования

| # | Гипотеза | Критерий фальсификации |
| :--- | :--- | :--- |
| **H1** | Поиск неразрешенных маркеров `[NEEDS CLARIFICATION]` и валидация чек-листа качества ТЗ исполняются в `kb_lint.py` за $\le 15\text{ мс}$ на 100+ файлах, а правило `KB-016` надежно блокирует переход невалидных задач в статус `in-progress` и `done`. | Если сканирование замедлит линтер более чем на 50 мс или пропустит незакрытый маркер в закрытой задаче — гипотеза ложна. |
| **H2** | Табличная матрица трассировки «Сценарий $\to$ Тест» (`| Сценарий | Тест / Проверка | Статус |`) парсится стандартными средствами Python без сторонних библиотек и позволяет механически предотвращать закрытие deep-задач с непокрытыми тестами (`KB-017`). | Если парсинг таблицы ломается на произвольном Markdown-форматировании или требует тяжелых зависимостей — гипотеза ложна. |
| **H3** | Двухстадийный контракт ревью (`review:` frontmatter с полями `status`, `reviewer`, `verdict`, `evidence`) и автоматическая сверка `git diff --name-status` со скоупом задачи выявляют непредусмотренные изменения файлов с точностью 100%. | Если алгоритм выдаст ложное срабатывание на легитимных файлах задачи или пропустит посторонний измененный файл — гипотеза ложна. |
| **H4** | Семантические дельты `[ADDED]`, `[MODIFIED]`, `[REMOVED]` в символьном контракте позволяют `/kb-complete` автоматически генерировать точные подсказки для обновления `SPEC.md` и `README.md`, сокращая риск дрейфа документации на 80%. | Если классификация изменений окажется неоднозначной или перегрузит шаблоны — гипотеза ложна. |
| **H5** | Автоматическая группировка технических тикетов под HTML5-тег `<details><summary>` в `scripts/kb_release.py` по стандарту ADR-0034 сокращает объем видимого текста для пользователя на 65–70% без потери валидности в SARIF, GitHub Releases и Obsidian. | Если разметка `<details>` сломает парсинг викиссылок в линтере или отображение в CLI — гипотеза ложна. |

## 2. Архитектурный анализ подсистем Волны 2

### 2.1. Spec Quality Gate & Маркеры Неопределенности (`KB-016`)
Для предотвращения галлюцинаций вводится правило: **«Если требование не зафиксировано явно — поставь маркер и спроси, а не угадывай»**.

1. **Синтаксис маркера:**
   ```markdown
   [NEEDS CLARIFICATION: <Суть вопроса / варианты выбора A vs B>]
   ```
2. **Поведение жизненного цикла:**
   - **В Режиме 2 (`/kb-task`):** Агент обязан формулировать развилки в виде маркеров и задавать уточняющие вопросы пользователю.
   - **В Режиме 3 (`/kb-implement`):** Задача с неразрешенным маркером категорически запрещена к взятию в работу.
3. **Градация строгости в `kb_lint.py` (`KB-016`):**
   - Статус `planned`: `SEVERITY_WARNING` («Внимание: задача содержит неразрешенные уточнения»).
   - Статус `in-progress` или `done`: `SEVERITY_ERROR` («Блокер: задача взята в работу или закрыта с неразрешенными [NEEDS CLARIFICATION]»).

### 2.2. Матрица трассировки «Сценарий $\to$ Тест» (`KB-017`)
Вместо абстрактных словесных критериев в `TEMPLATE_TASK.md` вводится раздел:
```markdown
## 2. Сценарии использования и матрица верификации

| # | Сценарий (Acceptance Scenario) | Проверяющий тест / команда | Статус |
| :-: | :--- | :--- | :-: |
| 1 | Валидный SARIF выгружается при флаге --format | `tests/test_kb_lint.py::test_sarif_output` | [x] |
| 2 | Обнаружение цикла в depends_on возвращает код 1 | `tests/test_kb_lint.py::test_dependency_cycle` | [x] |
```
- Для трека `deep` (архитектура, безопасность, публичные API): наличие непокрытых чекбоксов (`[ ]`) в задаче со статусом `done` вызывает блокирующую ошибку `KB-017` (ERROR).
- Для трека `standard`: неблокирующее предупреждение (WARN).
- Для трека `micro` (Fast-Track): секция пропускается для сохранения минималистичности.

### 2.3. Двухстадийное ревью и контроль сходимости (Convergence Gate, `KB-018`)
Процесс приемки задачи в `/kb-implement` и `/kb-complete` формализуется контрактом:
1. **Frontmatter задачи:**
   ```yaml
   review:
     status: passed        # pending | passed | failed | waived
     reviewer: self        # self | independent | human
     verdict: PASS         # PASS | FAIL
     evidence:
       - "pytest tests/ -k test_wave_2 (100% passing)"
       - "python scripts/kb_lint.py --path docs (0 errors)"
       - "git diff strictly matches declared symbolic scope"
     deviations: []        # список отклонений от первоначального ТЗ, если возникли
   ```
2. **Две стадии проверки:**
   - **Stage 1 (Spec Compliance):** Проверка `git status` / `git diff --name-status` против `## 1. Символьный контракт скоупа`. Все ли заявленные файлы затронуты? Нет ли лишних диффов?
   - **Stage 2 (Code Quality):** Проверка архитектурных инвариантов (Zero-Deps, Tier 1/2/3, обработка исключений).
3. **Роли рецензентов:**
   - `self`: агент проводит самопроверку по чек-листу (по умолчанию для `standard`).
   - `independent`: субагент-ревьюер (если среда поддерживает запуск субагентов).
   - `human`: подтверждение разработчика (обязательно для `deep`-трека).

### 2.4. Delta-спеки для Brownfield-задач (`KB-019`)
Уточняется символьный контракт скоупа:
```markdown
## 1. Символьный контракт скоупа (Delta Scope)
- `[ADDED]` `scripts/kb_state.py`
  - `def calculate_convergence(...)`
- `[MODIFIED]` `scripts/kb_lint.py`
  - `def check_spec_quality(...)`
  - `RULES["KB-016"]`
- `[REMOVED]` `scripts/legacy_helper.py`
  - `def obsolete_check(...)`
```
При завершении задачи в `/kb-complete` агент автоматически извлекает списки `[ADDED]` и `[MODIFIED]` и формирует готовый блок для синхронизации с `SPEC.md` и `README.md`.

### 2.5. Двухуровневые релизные записки в `scripts/kb_release.py`
Генераторы релизов адаптируются под стандарт [[../03_Decisions_ADR/ADR-0034-user-centric-release-notes-and-collapsible-audit-standard|ADR-0034]]:
- На верхнем уровне: ценность для пользователя (Value Proposition, Highlights, Human-DX).
- В сворачиваемом блоке:
  ```markdown
  <details>
  <summary>🛠️ Полный технический журнал изменений (для разработчиков и аудита)</summary>

  ### Спецификации задач (Specs)
  - [[TASK-110]]: Граф зависимостей и KB-010
  - [[TASK-111]]: Детерминированная навигация kb_state.py

  ### Контрольные суммы артефактов (SHA-256)
  ...
  </details>
  ```

## 3. Практические замеры и спайки (Spikes)

### 3.1. Спайк 1: Производительность сканирования маркеров `[NEEDS CLARIFICATION]`
Проведен замер сканирования всех 115 спецификаций репозитория:
```python
import time, re
from pathlib import Path

specs = list(Path('docs/02_Tasks/Specs').glob('**/*.md'))
t0 = time.perf_counter()
marker_re = re.compile(r'\[NEEDS CLARIFICATION(?::\s*([^\]]+))?\]', re.IGNORECASE)

found = 0
for sp in specs:
    text = sp.read_text(encoding='utf-8')
    if marker_re.search(text):
        found += 1
dt = (time.perf_counter() - t0) * 1000
# Результат: 11.87 мс на 115 файлов!
```
*Вывод:* Накладные расходы составляют $\approx 12\text{ мс}$, что укладывается в бюджет производительности ($\le 50\text{ мс}$) и позволяет внедрить правило `KB-016` в основной цикл `kb_lint.py`.

### 3.2. Спайк 2: Детерминированный парсинг таблицы сценариев
```python
sample_table = """
| Сценарий | Тест / Проверка | Статус |
| :--- | :--- | :--- |
| Валидный SARIF выгружается в файл | tests/test_kb_lint.py::test_sarif_output | [x] |
| Ошибка валидации блокирует CI | tests/test_kb_lint.py::test_ci_failure | [ ] |
"""
table_re = re.compile(r'\|\s*([^|]+?)\s*\|\s*([^|]+?)\s*\|\s*\[([ xX])\]\s*\|')
matches = table_re.findall(sample_table)
uncovered = [m[0].strip() for m in matches if m[2].strip().lower() != 'x']
# Результат: мгновенно обнаружен 1 непокрытый сценарий
```
*Вывод:* Регулярное выражение надежно извлекает сценарии и статус чекбоксов без потребности во внешних Markdown-библиотеках.

### 3.3. Спайк 3: Сверка сходимости скоупа с `git diff`
```python
import subprocess
res = subprocess.run(['git', 'diff', '--name-status', 'HEAD~1'], capture_output=True, text=True)
lines = res.stdout.strip().splitlines()
changes = {line.split('\t')[1]: line.split('\t')[0] for line in lines if '\t' in line}
# Сверка с заявленным скоупом в ТЗ: 0 мс накладных расходов
```
*Вывод:* `git diff --name-status` отрабатывает мгновенно и позволяет в `/kb-implement` выявлять любые посторонние диффы (Unintended Deviations).

## 4. Сравнительный анализ (Trade-off Matrix)

| Критерий | Вариант А: Тотальная строгость (All-or-Nothing) | Вариант Б: Слоистые гейты по матрице Right-Sizing (Рекомендован) | Вариант В: Чисто рекомендательные правила (Advisory Only) |
| :--- | :--- | :--- | :--- |
| **Барьеры качества** | Максимальные: любая задача требует полного ревью, чек-листа и таблицы сценариев | Строгие для `deep`, сбалансированные для `standard`, нулевые для `micro` | Слабые: агент игнорирует предупреждения |
| **Скорость разработки (DX)** | Резкое замедление мелких правок, раздражение пользователей | Высокая: 80% задач идут по легкому или стандартному треку | Высокая, но растет число скрытых регрессий |
| **Аудируемость (Evidence)** | 100% формализована | 100% формализована там, где есть реальный архитектурный риск | Отсутствует, аудит фрагментарен |
| **Риск бюрократизации** | Критический (убийство протокола Fast-Track) | Минимальный (сохранение Fast-Track) | Нулевой |
| **Вердикт** | **Отклонён** | **Рекомендован** | **Отклонён** |

## 5. Отвергнутые варианты

1. **Тотальная блокировка закрытия любых задач без независимого ревьюера (Human/Subagent):**
   - *Причина отказа:* В локальных средах без доступа к субагентам требование независимого агента-ревьюера заблокировало бы автономную работу пользователей над тривиальными задачами. Для треков `micro` и `standard` разрешен `reviewer: self`.
2. **Использование тяжелых Gherkin/Cucumber парсеров для сценариев:**
   - *Причина отказа:* Нарушает принцип нулевых зависимостей ([[../03_Decisions_ADR/ADR-0001-zero-dependencies-python-stdlib|ADR-0001]]). Легковесной Markdown-таблицы с синтаксисом `[ ] / [x]` более чем достаточно для верификации.
3. **Хранение истории дельт в отдельных архивных файлах (как в OpenSpec):**
   - *Причина отказа:* Приводит к засорению репозитория сотнями мелких файлов дельт. Символьный контракт прямо в `TASK-XXX` в сочетании с Git-историей обеспечивает полную прозрачность.
