## 1. Контекст и цели (Problem & Goals)

### Проблема
1. **Фантомный бэклог при новой установке (Clean Slate Scaffolding):**
   Инсталлятор генерирует в `Kanban.md` и `Roadmap.md` ссылки на несуществующие `PLAN-001-initial-mvp-setup` и `TASK-001-project-scaffolding`. Пользователь вынужден вручную удалять чужие шаблонные задачи перед тем, как сформулировать свою первую реальную идею.
2. **Опасность затирания при установке в существующие проекты (Brownfield Adoption):**
   При запуске в уже существующем репозитории с кодовой базой инсталлятор не учитывает наличие готового `README.md`, существующих правил линтинга или специфики каталогов. Нет интеллектуального распознавания стека проекта по маркерным файлам (`package.json`, `Package.swift`, `pyproject.toml`, `*.sln`). Отсутствует четкий сценарий для агента по первичному аудиту существующей кодовой базы.
3. **Отсутствие безопасного сценария обновления (Day 2 Operations):**
   При выходе новых версий `agent-docs-harness` (новые скиллы, улучшения правил агентов, обновление линтера `kb_lint.py`) у пользователя нет штатного способа обновить инфраструктуру (`install.py --update`) без риска затереть историю разработки, задачи и Devlog.
4. **Отсутствие автоматизации проверки качества в CI:**
   Линтер `kb_lint.py` работает только локально при ручном запуске. В командной разработке нет готового workflow для GitHub Actions, гарантирующего отсутствие сломанных вики-ссылок и невалидного frontmatter в Pull Request.

### Цель Фазы 3
Превратить `agent-docs-harness` в зрелый инструмент полного жизненного цикла:
1. Обеспечить кристально чистый старт (Clean Slate) для новых проектов с моментальным переходом к `/kb-plan`.
2. Реализовать интеллектуальное, неразрушающее подключение к существующим проектам (Brownfield) с автоопределением стека и сценарием экспресс-аудита архитектуры.
3. Внедрить режим бережного обновления компонентов харнесса (`install.py --update`).
4. Добавить интеграцию с GitHub Actions CI (`.github/workflows/kb-lint.yml`).

## 2. Обсуждение и ключевые решения (Q&A / Discussion)

* **Q1: Как должен выглядеть стартовый бэклог в режиме Clean Slate?**
  * **Решение:** В стартовом `Kanban.md` и `Roadmap.md` полностью исключаются ссылки на фиктивные `PLAN-001` и `TASK-001`. Бэклог инициализируется пустым, колонка `Done` содержит только отметку об инициализации базы знаний, а колонка `Backlog` содержит дружелюбный плейсхолдер с инструкцией: *«Создайте свой первый план через `/kb-plan <название>`»*. Линтер `kb_lint.py` сразу после установки подтверждает 0 ошибок и 0 битых ссылок.
* **Q2: Как реализовать автоопределение стека без внешних библиотек?**
  * **Решение:** Проверка наличия ключевых файлов в корне проекта с приоритетом наиболее специфичных маркеров:
    * `Package.swift` $\to$ Swift / Apple
    * `package.json` $\to$ Web / TypeScript
    * `pyproject.toml`, `requirements.txt`, `Pipfile` $\to$ Python
    * `*.sln`, `*.csproj` $\to$ .NET
    * `Cargo.toml`, `go.mod` $\to$ Generic
    В интерактивном мастере определенный стек подставляется как вариант по умолчанию (Default), экономя время пользователя.
* **Q3: Как защитить существующие файлы в brownfield-репозиториях?**
  * **Решение:** 
    * Если `README.md` уже существует, инсталлятор не затирает его, а аккуратно дополняет секцией `## 🧠 Docs-as-Code & AI Agent Disciplines` (или создает `README_DOCS.md` в зависимости от флагов).
    * Если файлы `.gitignore` существуют, записи харнесса (`.obsidian/workspace.json`, `scratch/` и т.д.) дописываются в конец файла (append-only), без удаления правил пользователя.
    * Генерируется специальный раздел в `Onboarding.md`: инструкция по первичному аудиту легаси-проекта агентом (экспресс-анализ архитектуры, заполнение `SPEC.md` и создание первого плана рефакторинга/развития).
* **Q4: Как разграничиваются файлы при выполнении `install.py --update`?**
  * **Решение:**
    * **Обновляются безопасно:** `docs/00_Templates/*`, `scripts/kb_lint.py`, `.agents/skills/*`, `.obsidian/graph.json`.
    * **Обновляются с бэкапом (`.bak`):** `AGENTS.md` и правила агентов (если пользователь вносил правки, сохраняется копия `AGENTS.md.bak`).
    * **СТРОГО НЕ ЗАТИРАЮТСЯ:** `docs/02_Tasks/*` (Kanban, Roadmap, Plans, Specs, Bugs), `docs/03_Decisions_ADR/*`, `docs/04_Research/*`, `docs/05_Testing/*`, `docs/Devlog.md`, `SPEC.md`, `docs/00_Index.md`.
* **Q5: Как оформляется интеграция с CI?**
  * **Решение:** Добавляется CLI-флаг `--ci [github|none]` и шаг мастера. При выборе `github` генерируется минималистичный `.github/workflows/kb-lint.yml`, запускающий `python scripts/kb_lint.py --path docs` на `ubuntu-latest` при push и pull_request.

## 3. Архитектурное влияние и критический анализ (Architectural Impact & Critical Review)

* **Затрагиваемые компоненты:**
  * `install.py` — обновление генерации стартовых файлов, логика детекта стека, опция `--update`, генерация CI workflow, флаги CLI.
  * `scripts/build_installer.py` — пересборка инсталлятора с обновленными шаблонами и структурой.
  * `tests/test_installer.py` — добавление тестов на чистый старт, автодетект стека, сохранение файлов в brownfield-проектах, процедуру `--update` и CI-workflow.
* **Отказ от оверинжиниринга:**
  * На этапе планирования рассмотрены и официально отклонены:
    * Встроенный web-визуализатор базы знаний $\to$ [[../../03_Decisions_ADR/ADR-0005-rejection-of-embedded-web-visualizer|ADR-0005]].
    * Встроенный генератор PDF-отчетов $\to$ [[../../03_Decisions_ADR/ADR-0006-rejection-of-standalone-pdf-report-generator|ADR-0006]].
  * Семантический контроль фаз и нишевые агенты отложены в Icebox бэклога для исключения расползания скоупа.
