# 🐞 Дефект: BUG-003 — Бесшумный откат в локальный режим при отсутствии GitHub CLI (gh) в `kb-release`

> **ID:** BUG-003 | **Критичность:** Medium | **Статус:** fixed  
> **Релиз:** v0.12.0 | **Блокер:** Нет

## 1. Симптомы и окружение
* **Симптом:** Шаблон скилла `/kb-release` полагается на команду `gh release create` для публикации релизов в режиме «GitHub Mode». Однако у многих пользователей (особенно на Windows) бинарник `gh` не установлен в PATH. При сбое вызова `gh` процедура бесшумно откатывается в «Local-Only Mode» вместо явного уведомления о недостающей зависимости. В результате агент пушит Git-тег в remote-репозиторий, но не публикует Release Notes и артефакты на страницу GitHub Releases, при этом ложно сообщает пользователю об успешном выпуске релиза.
* **Окружение:** Windows / Linux / macOS без установленного `gh`, `scripts/kb_release.py`, скилл `kb-release`.

## 2. Шаги воспроизведения (Repro Steps)
1. Инициализировать Docs-as-Code в проекте с GitHub origin.
2. Убедиться, что `gh` CLI не установлен или не доступен в PATH.
3. Запустить процедуру релиза: `/kb-release v1.0.0`.
4. **Фактическое поведение:** Скрипт выполняет pre-flight проверки, генерирует `dist/`, пытается вызвать `gh release create`, ловит сбой и пушит только тег, рапортуя об успехе без создания страницы релиза на GitHub.
5. **Ожидаемое поведение:** Процесс релиза не должен скрывать сбой: либо выполнять публикацию через нативный Python-скрипт с GitHub REST API (`urllib`), либо на этапе Environment Detection прерывать процесс с понятной инструкцией по установке `gh` (`winget install GitHub.cli` / `brew install gh`).

## 3. Диагностика (Логи, Стек-трейс)
Отсутствие проверки доступности `gh` до начала публикации и неявный перехват исключений приводят к несогласованному состоянию: тег в Git создан, а релиз на GitHub отсутствует.

## 4. Первопричина (Root Cause Analysis — RCA)
В `scripts/kb_release.py` и процедуре скилла `kb-release` отсутствует валидация готовности внешнего инструмента публикации перед переходом к деструктивным/удаленным операциям, а обработка ошибок маскирует отсутствие бинарника под штатный локальный режим.

## 5. План исправления
* `[MODIFY]` `scripts/kb_release.py` — добавить функцию проверки наличия `gh` или прямую публикацию через GitHub REST API без внешних бинарников.
* `[MODIFY]` `.agents/skills/kb-release/SKILL.md` — обновить протокол pre-flight валидации.
* `[NEW]` `tests/test_kb_release.py` — регрессионный тест на явную ошибку / предупреждение при отсутствии `gh` в GitHub-репозитории.
