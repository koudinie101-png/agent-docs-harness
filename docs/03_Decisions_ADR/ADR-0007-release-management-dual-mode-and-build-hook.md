# ADR-0007: Архитектура релиз-менеджмента (Dual-Mode: GitHub / Local-Only и Build Hook Contract)

> **Статус:** Принято  
> **Дата:** 2026-10-01  
> **Теги:** #adr #architecture #release-management #github #build-hook #docs-as-code  
> **Первоисточник исследования:** [[../../04_Research/RESEARCH-002-release-management-and-github-automation|RESEARCH-002: Архитектура подготовки релиза]]  
> **Связанные решения:** [[ADR-0001-zero-dependencies-python-stdlib|ADR-0001: Zero Dependencies]]  

---

## 1. Контекст и проблема

В текущем жизненном цикле Docs-as-Code задачи переходят через 3 режима: `/kb-plan` (Режим 1) -> `/kb-task` (Режим 2) -> `/kb-implement` и `/kb-complete` (Режим 3). Задачи группируются по фазам в [[../02_Tasks/Roadmap|Дорожной карте]].

Однако в момент завершения всех задач фазы возникал процессный и архитектурный пробел:
1. **Отсутствие формализованного релиза:** Завершение фазы не сопровождалось созданием релизных артефактов, фиксацией тегов и отчетом о поставленной ценности.
2. **Дилемма среды:** Часть проектов хостится на GitHub и требует GitHub Releases с аттачами и релизными заметками. Другая часть проектов — оффлайн, локальные или корпоративные контуры (Local-Only), где внешние сервисы недоступны, но необходима сборка исполняемого файла с указанием локального пути, размера и контрольной суммы.
3. **Разнородность стеков:** Проекты на Swift, Python, TypeScript, .NET, Rust собираются разными компиляторами и флагами.
4. **Риск неявной автоматизации:** Предложение автоматически триггерить релиз при закрытии последней задачи фазы в `kb-complete` несет критические риски (блокировка закрытия ТЗ при сбоях компиляции, пропуск E2E UX тестирования, неопределенность SemVer).

---

## 2. Решение

Принята следующая целевая архитектура релиз-менеджмента:

1. **Явный триггер через скилл `/kb-release`:**
   * Отказаться от неявного авторелиза при закрытии тикетов в `kb-complete`.
   * Релиз инициируется строго явно вызовом `/kb-release <vX.Y.Z>` после успешного выполнения приемочных сценариев из `docs/05_Testing/`.
   * В `kb-complete` внедряется неблокирующая подсказка (Nudge): если закрыта последняя задача фазы, агент выводит рекомендацию провести E2E тестирование и вызвать `/kb-release`.

2. **Двухуровневая архитектура публикации (Dual-Mode Engine):**
   * **GitHub Mode (Remote / CI):** При наличии настроенного `origin` на github.com и утилиты `gh`:
     * Создается аннотированный Git-тег `vX.Y.Z`.
     * Пушится тег в remote.
     * Создается релиз через `gh release create vX.Y.Z dist/* --notes-file ...` (либо пуш тега активирует шаблон GitHub Actions `.github/workflows/release.yml`).
   * **Local-Only Mode (Offline / Enterprise):** Если Git remote отсутствует или `gh` недоступен:
     * Выполняется локальный сборочный хук.
     * Сканируется каталог `dist/`, вычисляются размеры и **SHA-256** хэши файлов.
     * Формируется локальный документ релиза с точными путями к файлам на диске.

3. **Контракт сборочного хука (Build Hook Contract — Convention over Configuration):**
   * Все скомпилированные бинарники и пакеты приложения помещаются в стандартный каталог `dist/` в корне проекта (включен в `.gitignore`).
   * Точка входа сборки определяется последовательно:
     1. Скрипт сборки проекта: `scripts/build_release.py` или `scripts/build_release.sh`.
     2. Конфигурация манифеста: `package.json` (`npm run build`), `Makefile` (`make release`), `pyproject.toml` (`python -m build`), `Package.swift` (`swift build -c release`), `*.sln` (`dotnet publish -c Release -o ./dist`), `Cargo.toml` (`cargo build --release`).
     3. Если хук не найден — формируется документарный Source Release (Git-тег и чейнджлог).

4. **Интеграция в базу знаний Docs-as-Code:**
   * Новый канонический шаблон: `docs/00_Templates/TEMPLATE_RELEASE.md`.
   * Постоянный каталог релизов: `docs/02_Tasks/Releases/` с файлами `RELEASE-vX.Y.Z.md` (Permalinks).
   * Автоматическая семантическая агрегация чейнджлога из завершенных `TASK-XXX`, `BUG-XXX` и `ADR-XXXX` текущей фазы.
   * Синхронизация с корневым `CHANGELOG.md`, канбаном [[../02_Tasks/Kanban|Kanban.md]] и [[../02_Tasks/Roadmap|Roadmap.md]].

## 3. Рассмотренные и отвергнутые варианты (Considered & Rejected Alternatives)

* ❌ **Неявный авторелиз внутри `kb-complete` при закрытии последней задачи фазы:**
  * *Причины отклонения:* Прямое нарушение принципа наименьшего удивления (POLA). Блокирует проведение приемочного E2E тестирования перед публикацией. В случае сбоя компиляции или сети задача не может быть отмечена как выполненная. Отсутствует возможность осознанного выбора версии (SemVer: мажор, минор, патч).
* ❌ **Использование тяжелых внешних npm/Go утилит (`semantic-release`, `release-it`, `goreleaser`):**
  * *Причины отклонения:* Нарушение [[ADR-0001-zero-dependencies-python-stdlib|ADR-0001: Zero Dependencies]]. Недопустимо принуждать разработчиков на Swift, Python или .NET устанавливать рантайм Node.js и десятки сторонних пакетов ради релиза.
* ❌ **Хранение скомпилированных артефактов в ветках Git:**
  * *Причины отклонения:* Раздувание размера репозитория, проблемы с лимитами GitHub (100 MB), конфликты слияния бинарных файлов. Артефакты должны храниться в `dist/` (локально) или в GitHub Release Assets.
* ❌ **Хардкод флагов компиляции всех языков программирования в ядро инсталлятора:**
  * *Причины отклонения:* Невозможно поддержать тысячи вариаций флагов Xcode, MSBuild, Cargo. Контракт точки входа (`scripts/build_release.py` / `dist/`) дает полную гибкость и изолированность.

## 4. Обоснование и последствия

### Плюсы:
* **Полная предсказуемость:** Разработчик и агент сохраняют полный контроль над моментом релиза и номером версии.
* **Универсальность и автономность:** Одинаково надежно работает на GitHub, в закрытых корпоративных сетях и на полностью изолированных оффлайн-машинах.
* **Семантическая чистота чейнджлогов:** Релизные заметки строятся на структурированных данных Docs-as-Code (`TASK-XXX`, `BUG-XXX`, `ADR-XXXX`), а не на замусоренной истории git-коммитов.
* **Безопасность:** Локальная машина не обязана содержать боевые ключи подписи — для GitHub-проектов релизная сборка делегируется защищенному CI.

### Минусы и риски:
* **Дополнительный ручной шаг:** Инженеру необходимо вызвать команду `/kb-release vX.Y.Z` вместо полной магии «все само при закрытии тикета» (компенсируется подсказкой-напоминанием в `kb-complete`).
* **Необходимость поддержки каталога `dist/`:** Проекты со специфичной структурой сборки должны обеспечить складывание артефактов в `dist/` либо реализовать `scripts/build_release.py`.
