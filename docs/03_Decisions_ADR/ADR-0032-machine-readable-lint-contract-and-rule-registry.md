# ADR-0032: Машинно-читаемый контракт линтера (Finding + KB-XXX + text/json/sarif)

> **Статус:** Принято | **Дата:** 2026-10-25  
> **Задача:** [[../02_Tasks/Specs/27_DocsIntegrity/TASK-101-finding-model-rule-registry-and-formats|TASK-101]] | **План:** [[../02_Tasks/Plans/PLAN-025-docs-integrity-gate-kb-lint-productization|PLAN-025]]  
> **Исследование:** [[../04_Research/RESEARCH-027-competitor-best-practices-and-adoption-backlog|RESEARCH-027]] (§4 Волна 1 п.1, §5.1)

## 1. Контекст и проблема

`scripts/kb_lint.py` — единственный Tier 1-гейт базы знаний, но наружу он отдавал только человекочитаемый текст и код возврата: 74 вызова `print()`, 15 `check_*`-функций возвращали предформатированные строки (часть — с легаси-префиксом `WARN:`). Следствия:

* CI, GitHub Code Scanning и любые агрегаторы диагностики получают «что-то не так» без правила, файла и категории.
* Любая новая проверка (`KB-010` для `depends_on`, right-sizing-предупреждения, spec quality gate) осталась бы строкой в тексте: привязать к ней ignore-лист, severity-политику или pre-commit-конфиг невозможно.
* Машинно-читаемый отчёт нельзя получить, не парся эмодзи и отступы.

Ограничения: Zero-Dependencies ([[ADR-0001-zero-dependencies-python-stdlib|ADR-0001]]), Python 3.8+, неизменный text-вывод (его проверяют 60 тестов и два CI-workflow), запрет номеров строк как ориентира ([[ADR-0029-fine-grained-task-symbol-contracts-and-line-drift-rejection|ADR-0029]]).

## 2. Решение

1. **Единая модель находки.** Все проверки возвращают `List[Finding]`, где `Finding` — подкласс `str` с атрибутами `rule_id`, `severity`, `file` и свойством `message`. Наследование от `str` — осознанный компромисс: `check_*` исторически возвращали списки сообщений, и потребители (60 тестов, клиентские скрипты в установленных проектах) сравнивают их как строки. Это сохраняет обратную совместимость вспомогательного API без правки ассертов, при этом JSON/SARIF-рендереры читают структуру, а не текст.
2. **Реестр правил — SSOT.** `RULES` (`KB-001…KB-015`) + `RULE_SEVERITY`; `make_finding()` валидирует `rule_id` и `severity` и бросает `ValueError` при нарушении. `KB-010` присутствует в `RULES`, но не имеет severity: попытка эмиссии — ошибка, поэтому зарезервированное правило не может «просочиться» раньше `depends_on`.
3. **Один отчёт — три рендерера.** `LintReport(files, wikilinks, findings)`; `render_text()` воспроизводит прежний вывод байт-в-байт (silent и verbose), `render_json()` отдаёт схему `version: 1` (`summary`, `errors[]`, `warnings[]`), `render_sarif()` — минимальный SARIF 2.1.0 без `region.startLine` и без `informationUri`.
4. **CLI:** `--format {text,json,sarif}` (default `text`), `--version` печатает версию набора правил (`kb_lint 1`). Exit-коды не зависят от формата; при `--format ≠ text` на stdout попадает только документ, `--verbose` — no-op.

## 3. Отвергнутые варианты (Rejected Alternatives)

* **Парсинг готовых строк регулярками:** хрупко (пути в кавычках, эмодзи, вложенные скобки), и структура восстанавливается догадкой, а не фактом.
* **Гибрид «старые проверки — строки, новые — находки»:** две параллельные абстракции одного понятия; нарушает Prior-Art Gate и правило 14 `AGENTS.md`.
* **Отдельный `kb_lint_json.py`:** дублирование проверок в бандле, гарантированный рассинхрон и четвёртый файл в `build_installer.py`.
* **`NamedTuple`-модель с миграцией 75 вызовов в тестах:** ломает обратную совместимость вспомогательного API и требует правки ассертов — ровно того, что задача запрещала.
* **Поля `line` и `fixable` «на будущее»:** всегда `null`/`false` — ложное обещание точности; появятся вместе с реализацией.
* **SARIF с фиктивным `startLine: 1`:** хуже отсутствия локации; аннотации указывали бы на первую строку файла.
* **`informationUri` с URL проекта:** установленная копия линта не должна выдавать происхождение проекта (прецедент утечки метаданных — BUG-009).
* **`jsonschema` для валидации SARIF:** нарушение [[ADR-0001-zero-dependencies-python-stdlib|ADR-0001]].
* **Хардкод релизной версии в `--version`:** версии-SSOT в репозитории нет, значение разъедется с тегом; релизная версия — задача пункта `doctor` в Icebox.
* **Нормализация текста сообщений (удаление `WARN:`):** изменила бы text-вывод и потребовала правки 60 ассертов; префикс остаётся частью `message`, семантику несёт `severity`.

## 4. Последствия

* **Плюсы:** линт становится пригодным для CI/Code Scanning; появляется словарь стабильных `KB-XXX` для ignore-листов, severity-политик и следующих проверок; text-паритет подтверждён байт-в-байт (старый и новый скрипт дают идентичный stdout в silent и verbose); единый источник правды для трёх форматов.
* **Минусы / Компромиссы:**
  * `Finding(str)` — переходный тип: равенство и сортировка игнорируют метаданные. Это цена обратной совместимости; при мажорном релизе тип можно ужесточить.
  * SARIF без регионов: аннотации указывают на файл, а не на строку — `DEBT-004` (`P3`).
  * `KB-010` присутствует в реестре, но не эмитится: тест на «нет эмиссии» обязателен (TASK-102).
  * `--version` сообщает версию набора правил, а не релиза; потребность в релизной версии остаётся открытой до появления `doctor`.
* **Область:** `--fix`, `action.yml` и `.pre-commit-hooks.yaml` остаются в Icebox (Волна 1, остаток); бюджет монолита `install.py` пере-базируется в `TASK-103`.
