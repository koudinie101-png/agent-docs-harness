# ADR-0035: Стандарт навигации и графа зависимостей Волны 1 (kb_state, depends_on, kb_lint --fix)

> **Статус:** Принято | **Дата:** 2026-11-19

## 1. Контекст и проблема

Развитие экосистемы Docs-as-Code выявило три узких места в эргономике взаимодействия агентов и разработчиков:
1. **Агентская дезориентация и перерасход токенов:** При завершении задачи агент не имеет одного стабильного источника правды для ответа на вопрос «Какую задачу делать дальше?». Он сканирует Kanban, планы, баги и спецификации, тратя контекстное окно и совершая ошибки маршрутизации.
2. **Отсутствие графа зависимостей (`depends_on`):** Ни линтер, ни агент не контролируют очередность выполнения взаимосвязанных задач. Это создает риск преждевременного старта интеграционных задач до реализации их архитектурных фундаментов.
3. **Рутина сопровождения связности базы знаний:** Мелкие детерминированные дефекты (переименование файла, битая относительная ссылка, пропущенное обязательное поле frontmatter) требуют ручного вмешательства человека или дополнительных turn'ов диалога с агентом.

По итогам сравнительного аудита лучших практик конкурентов ([[../04_Research/RESEARCH-027-competitor-best-practices-and-adoption-backlog|RESEARCH-027]]) сформирована инициатива **Волна 1 (Docs Integrity Gate)**.

## 2. Решение

Утвержден архитектурный стандарт компонентов Волны 1:

### 2.1. Специализированная утилита навигации `scripts/kb_state.py`
Создается автономная утилита на стандартной библиотеке Python 3, реализующая команды:
* `kb_state status` — оперативная сводка состояния: текущая фаза, выполненные/активные/заблокированные задачи, открытые баги.
* `kb_state next` — детерминированный выбор следующей готовой к работе задачи с учетом графа зависимостей и критических дефектов (P0 баги $\to$ активная задача $\to$ первая разблокированная задача).
* `kb_state next --json` — компактный контракт для автоматических тул-колов агентов.
* `kb_state context TASK-XXX` — сборка целевого контекста задачи без информационного шума.

### 2.2. Машинно-читаемый граф зависимостей (`depends_on` и `KB-010`)
1. Во frontmatter спецификаций задач (`docs/00_Templates/TEMPLATE_TASK.md`) вводится поле `depends_on: [TASK-XXX, ...]`.
2. В `scripts/kb_lint.py` реализуется зарезервированное правило **`KB-010`**:
   - Обнаружение циклических зависимостей с помощью обхода в глубину (DFS) и точным выводом пути цикла (`TASK-A -> TASK-B -> TASK-A`).
   - Валидация существования идентификаторов (запрет висячих ссылок на несуществующие задачи).
3. Карточки задач в `Kanban.md` получают визуальный статус блокировки (`🔒 [blocked by TASK-XXX]`), а команда `kb_state next` исключает заблокированные задачи из рекомендаций к старту.

### 2.3. Консервативное автоисправление `scripts/kb_lint.py --fix`
1. Автоисправление ограничивается исключительно 100% однозначными детерминированными операциями:
   - Обновление битых викиссылок при однозначном переименовании/перемещении целевого файла (`KB-001`).
   - Заполнение отсутствующих обязательных полей frontmatter значениями по умолчанию (`KB-003`).
   - Нормализация окончаний строк и удаление висячих пробелов.
2. Безопасность выполнения:
   - Флаг `--dry-run` активен по умолчанию (показ diff).
   - Реальное применение требует флага `--apply` (или `-y`).
   - Обязательное создание резервной копии `.bak` перед изменением файла на диске.

### 2.4. Матрица гибкости жизненного цикла (Right-Sizing Matrix)
Фиксируются 3 канонических трека разработки:
1. **Micro (Fast-Track):** $\le 30$ LOC, $\le 2$ файла, 0 архитектурных рисков (`/kb-task --fast` $\to$ `/kb-implement`).
2. **Standard:** типовая фича, $\le 300$ LOC внутри модуля (ТЗ $\to$ реализация с TDD).
3. **Deep (High-Risk):** изменения ядра, смена публичных API или контрактов (обязательный `/kb-research` $\to$ `/kb-plan` $\to$ `/kb-task` $\to$ `/kb-implement` с независимым ревью). Линтер предупреждает о нарушениях правилом `KB-016`.

## 3. Отвергнутые варианты (Rejected Alternatives)

* ❌ **Хранение состояния в центральной базе SQLite или файле `kb_state.json`:**  
  *Причины отклонения:* Риск дрейфа и рассинхронизации с Git-деревом при слиянии веток. Прямой парсинг файлов спецификаций занимает $< 50\text{ мс}$, что делает внешнюю базу избыточной.
* ❌ **Автоматический разрыв циклических зависимостей:**  
  *Причины отклонения:* Разрыв цикла — это содержательное архитектурное решение человека о приоритетах систем. Автоматическое удаление связей недопустимо.
* ❌ **Агрессивный AI-автофикс с генерацией пропущенных файлов:**  
  *Причины отклонения:* Высокий риск галлюцинаций и скрытого засорения базы знаний непроверенными артефактами.

## 4. Последствия

### Плюсы:
* **Однозначность для агента:** Команда `kb_state next` снимает когнитивную нагрузку и исключает случайный запуск неподготовленных задач.
* **Структурная строгость:** Граф зависимостей и правило `KB-010` механически гарантируют правильный порядок проектирования и реализации.
* **Экономия времени:** Безопасный `--fix` мгновенно устраняет рутинные опечатки в ссылках без ручного редактирования.
* **Прагматизм процессов:** Матрица Right-Sizing предотвращает бюрократический перегруз для мелких задач.

### Минусы / Накладные расходы:
* Необходимость поддержки дополнительной утилиты `scripts/kb_state.py` в инсталляторе и бандле (`install.py`).
* Требование аккуратного указания `depends_on` при проектировании зависимых модулей.
