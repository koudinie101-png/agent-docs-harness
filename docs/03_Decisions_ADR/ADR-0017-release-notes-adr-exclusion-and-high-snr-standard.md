# ADR-0017: Исключение секции архитектурных решений (ADR) из публичных релизных заметок

> **Статус:** Принято | **Дата:** 2026-10-02  
> **Первоисточник исследования:** [[../04_Research/RESEARCH-013-release-notes-adr-exclusion-and-high-snr|RESEARCH-013: Оптимизация публичных релизных заметок]]  
> **Связанные решения:** [[ADR-0009-high-snr-token-architecture-and-context-efficiency|ADR-0009: High-SNR Architecture]], [[ADR-0010-github-release-notes-and-public-distribution-standard|ADR-0010: GitHub Release Standard]]  

---

## 1. Контекст и проблема

В ходе аудита публичных релизов `v0.7.0` и `v0.8.0` на GitHub обнаружено избыточное раздувание описания:
В сгенерированном `dist/RELEASE_NOTES.md` под заголовком `### 🏛️ Архитектурные решения (ADR)` выводился кумулятивный список из 14–16 решений за всю историю проекта.

Причины и последствия:
1. **Смешение целевых аудиторий:** Публичный чейнджлог на GitHub адресован конечным пользователям и интеграторам. Внутренние ADR адресованы мейнтейнерам и разработчикам базы знаний Docs-as-Code.
2. **Падение плотности полезного сигнала (Low SNR):** Список ADR занимал до 45% объема заметки, вытесняя критически важные блоки быстрого старта (`curl ... | python3`) и контрольные суммы SHA-256 за границы первого экрана.
3. **Противоречие стандарту Keep a Changelog:** Общепринятые стандарты не включают архитектурные решения в публичные чейнджлоги.

---

## 2. Решение

1. **Исключение секции ADR из публичного генератора заметок:**
   В функции `generate_public_release_notes()` утилиты `scripts/kb_release.py` полностью упразднить секцию `### 🏛️ Архитектурные решения (ADR)`.
2. **Инлайн-трассировка по необходимости:**
   Если архитектурное решение критично для контекста конкретной пользовательской возможности, ссылка на соответствующий ADR включается инлайн непосредственно в описание задачи (`TASK-XXX`).
3. **Сохранение чистоты внутреннего архива:**
   Во внутреннем архивном документе `docs/02_Tasks/Releases/RELEASE-vX.Y.Z.md` исключить кумулятивный сбор всех исторических решений; собирать только ADR, относящиеся непосредственно к текущей фазе релиза.

---

## 3. Отвергнутые варианты (Rejected Alternatives)

* ❌ **Сохранение кумулятивного списка ADR (как было):**  
  *Причины отклонения:* Неограниченный $O(N)$ рост визуального мусора при каждом релизе, нарушение принципа High-SNR (ADR-0009).
* ❌ **Фильтрация ADR строго по фазе в публичных заметках:**  
  *Причины отклонения:* Пользователю все еще не интересны внутренние архитектурные документы, если они не меняют публичный контракт; дублирование содержания задач.
* ❌ **Сворачивание ADR под HTML-спойлер `<details>`:**  
  *Причины отклонения:* Половинчатое решение, загромождает Markdown и не решает проблему расхода токенов в контексте автоматических парсеров.

---

## 4. Последствия

### Плюсы:
* **Кристально чистый чейнджлог:** Заметки релиза на 45% компактнее, структурированы строго по канону (Features, Fixes, SHA-256).
* **Мгновенный доступ к проверке:** Таблица SHA-256 и сниппет верификации видны на первом экране.
* **100% соответствие High-SNR (ADR-0009):** Устранен информационный шум для пользователей и AI-агентов.

### Минусы / Компромиссы:
* Разработчикам, желающим изучить архитектурные изменения релиза, необходимо открывать каталог `docs/03_Decisions_ADR/` в репозитории (что является естественным поведением для контрибьюторов).
