# ADR-0008: Архитектура каналов обратной связи, буфера триажа и локальной диагностики

> **Статус:** Принято  
> **Дата:** 2026-10-01

> **Связанные решения:** [[ADR-0001-zero-dependencies-python-stdlib|ADR-0001: Zero Dependencies]], [[ADR-0007-release-management-dual-mode-and-build-hook|ADR-0007: Release Management]]

## 1. Контекст и проблема

После выпуска релизов (как в виде открытого репозитория на GitHub, так и при локальном распространении `install.py` среди коллег и друзей) проект сталкивается с входящим потоком внешних сигналов: сообщениями об ошибках, предложениями по доработке и вопросами по использованию.

В методологии Docs-as-Code кодовая база защищена строгим регламентом 3 режимов, каноническими ТЗ (`TASK-XXX`), баг-репортами (`BUG-XXX`) с обязательным TDD-принципом Regression-First и [[../02_Tasks/Roadmap|Дорожной картой]].

Возникли следующие проблемы:
1. **Риск деградации базы знаний:** Прямое занесение каждого входящего отзыва в производственные файлы `BUG-XXX` или Канбан несет угрозу замусоривания: 70–80% тикетов от внешних пользователей содержат невоспроизводимые данные, являются ошибками окружения или дубликатами.
2. **Отсутствие канала связи в оффлайн/Local-Only режиме:** При передаче скрипта `install.py` друзьям или коллегам без Git и GitHub, пользователь при сбое сообщает лишь «у меня не работает». Разработчик тратит часы на выяснение версий Windows, Python, локалей и трассировок.
3. **Размытие ответственности в GitHub:** Сваливание вопросов, идей и дефектов в единый список GitHub Issues приводит к перегрузке трекера и потере критических багов.

---

## 2. Решение

Принята архитектура **трехуровневой воронки триажа (Triage Funnel)** и разделения каналов обратной связи:

1. **Отказ от прямого внесения сырых сигналов в трекинг задач:**
   * Вводится обязательный промежуточный буфер ожидания (**Triage Buffer**):
     - В базе знаний: локальный каталог `docs/02_Tasks/Inbox/` (файлы `FB-YYYYMMDD-<slug>.md`).
     - В GitHub: метка `needs-triage` на входящих issues.
   * Сырые сигналы не становятся тикетами `BUG-XXX` или задачами Канбана до прохождения сессии триажа.

2. **Разделение потоков на GitHub (Discussions vs Issue Forms):**
   * **GitHub Discussions:** выступает фильтром для свободного общения:
     - Категория `Ideas` — предложения фичей с голосованием сообщества апвоутами (Upvotes).
     - Категория `Q&A` — вопросы по установке и настройке.
   * **GitHub Issues:** используется строго для воспроизводимых дефектов через декларативные веб-формы `.github/ISSUE_TEMPLATE/bug_report.yml` с обязательными валидируемыми полями (ОС, версия, шаги, логи).
   * В `.github/ISSUE_TEMPLATE/config.yml` отключается возможность создания пустых тикетов (`blank_issues_enabled: false`), а пользователи с вопросами перенаправляются в Discussions.

3. **Локальный диагностический бандл для Local-Only / друзей (`install.py --report`):**
   * В автономный скрипт `install.py` внедряется механизм генерации безопасного отчета:
     - Запуск по явному флагу `python install.py --report` либо интерактивное предложение при падении скрипта.
     - Безопасный сбор системных данных без сторонних зависимостей (OS Platform/Release, Python version, stdout/locale encoding, Traceback).
     - Формирование локального файла `feedback_report_<timestamp>.md` без приватных данных и секретов.
     - Пользователь отправляет готовый файл автору через привычный мессенджер (Telegram, Email) или локальную сеть.
     - Автор помещает файл в `docs/02_Tasks/Inbox/`.

4. **Инженерный конвейер триажа (Скилл `/kb-triage`):**
   * Разрабатывается скилл агента `/kb-triage`, автоматизирующий обработку очередей из `docs/02_Tasks/Inbox/` и `gh issue list`:
     - **Критический дефект:** формирует `docs/02_Tasks/Bugs/BUG-XXX` по шаблону `TEMPLATE_BUG.md`, ставит задачу в Канбан и обязывает написать регрессионный тест (Regression-First).
     - **Ценная идея / фича:** переносится в `docs/02_Tasks/Roadmap.md` в секцию «🔮 Перспективные направления (Icebox)» для последующего планирования в Режиме 1 (`/kb-plan`).
     - **Вопрос / ошибка пользователя:** генерирует проект разъяснения, при необходимости обновляет документацию онбординга (`Onboarding.md`) и закрывает тикет.

## 3. Рассмотренные и отвергнутые варианты (Considered & Rejected Alternatives)

* ❌ **Прямая автоматическая конвертация входящих GitHub Issues в файлы `BUG-XXX`:**  
  * *Причины отклонения:* Засорение базы знаний невоспроизводимым мусором, ложными срабатываниями и дубликатами. Нарушение принципа детерминированности и чистоты репозитория.
* ❌ **Вшивание токенов Telegram-бота или Webhook в открытый код `install.py`:**  
  * *Причины отклонения:* Фатальная уязвимость безопасности. Токены из открытого скрипта могут быть мгновенно извлечены третьими лицами, что приведет к компрометации бота, спам-атакам и блокировке. Кроме того, сетевой запрос упадет в изолированных оффлайн-сетях.
* ❌ **Сваливание идей и дефектов в единый трекер GitHub Issues:**  
  * *Причины отклонения:* Размытие фокуса разработки. Дефекты требуют срочной TDD-фиксации, а идеи — стратегической оценки и голосования. Идеи должны жить в GitHub Discussions до момента одобрения в Roadmap.
* ❌ **Подключение тяжелых внешних Helpdesk платформ (Zendesk, Jira Service Desk, Intercom):**  
  * *Причины отклонения:* Избыточный оверинжиниринг, нарушение [[ADR-0001-zero-dependencies-python-stdlib|ADR-0001: Zero Dependencies]] и потеря автономности локального Docs-as-Code.

## 4. Обоснование и последствия

### Плюсы:
* **Изоляция базы знаний:** Чистота Канбана и ТЗ гарантируется промежуточным буфером триажа.
* **Идеальный UX для оффлайн/друзей:** Другу достаточно нажать `y` при ошибке или выполнить `install.py --report`, чтобы получить файл с исчерпывающей диагностикой кодировок и окружения.
* **Сфокусированный бэклог:** Дорожная карта пополняется только валидированными, полезными идеями, прошедшими через сито триажа или голосование в Discussions.
* **Нулевые зависимости и безопасность:** Нет скрытой телеметрии, нет вшитых секретов, 100% реализация на стандартной библиотеке Python.

### Минусы и риски:
* **Необходимость регулярных сессий триажа:** Накопление файлов в `docs/02_Tasks/Inbox/` требует периодического запуска скилла `/kb-triage`.
* **Дополнительные шаблоны в инсталляторе:** Потребуется поддерживать генерацию каталога `.github/ISSUE_TEMPLATE/` для целевых проектов, использующих Git/GitHub.
