# ADR-0027: Task-Scoped пространства имен визуальных макетов (`TASK-XXX/`), жизненный цикл As-Is/To-Be и валидация топологии `docs/assets/` в `kb_lint.py`

> **Статус:** Принято | **Дата:** 2026-10-15  
> **Основание:** [[../04_Research/RESEARCH-022-asset-storage-hardening-and-task-scoped-namespaces|RESEARCH-022]], [[../02_Tasks/Inbox/FB-GH-5|FB-GH-5]] | **Развивает:** [[ADR-0026-heterogeneous-ui-ux-and-visual-asset-management|ADR-0026]]

---

## 1. Контекст и проблема

В [[ADR-0026-heterogeneous-ui-ux-and-visual-asset-management|ADR-0026]] был введен стандарт хранения визуальных ассетов в `docs/assets/` с разделением на `mockups/<target>/`, `mockups/flows/`, `screenshots/<target>/TASK-XXX.png` и `screenshots/multi-device/TASK-XXX.png`.

Опыт применения `ADR-0026` в гетерогенных проектах ([[../02_Tasks/Inbox/FB-GH-5|FB-GH-5]]) и стресс-тестирование в [[../04_Research/RESEARCH-022-asset-storage-hardening-and-task-scoped-namespaces|RESEARCH-022]] выявили три архитектурных пробела:
1. **Дрифт и перезапись макетов при итеративных редизайнах («To-Be Drift»):** плоская структура `docs/assets/mockups/<target>/<screen>_tobe.svg` работает только при первой разработке экрана. При повторном редизайне того же экрана в последующих фазах перезапись файла ломает исторический контракт предыдущей задачи (нарушая *Permalinks Principle*), а ручное добавление суффиксов (`_v2`, `_final`) ведет к хаосу.
2. **Появление «диких» корневых папок (Rogue Roots):** в отсутствие стандарта группировки внутри `mockups/<target>/` для приложений с множеством поверхностей разработчики и агенты ошибочно создают папки платформ и компонентов прямо в корне `docs/assets/<target>/<component>/`.
3. **Ложноположительное разрешение путей в `kb_lint.py` и отсутствие контроля топологии:** при использовании унифицированных имен (`asis.svg`, `tobe.svg`) в разных подпапках `TASK-XXX/` текущий `scripts/kb_lint.py` разрешал битые относительные ссылки `![[../../../assets/mockups/android/TASK-098/tobe.svg]]` за счет совпадения голого имени `tobe.svg` в `file_map` от другой задачи (`TASK-047/tobe.svg`), а также не проверял структуру папок внутри `docs/assets/`.

---

## 2. Решение

Принять архитектуру **Task-Scoped Visual Asset Namespaces** как расширение и уточнение [[ADR-0026-heterogeneous-ui-ux-and-visual-asset-management|ADR-0026]]:

### 2.1. Каноническая топология `docs/assets/` и симметрия `TASK-XXX`

Установить полную структурную симметрию между спецификациями (`Specs/.../TASK-XXX.md`), макетами (`mockups/.../TASK-XXX/`) и подтверждающими скриншотами (`screenshots/.../TASK-XXX.png`):

```text
docs/assets/
├── mockups/
│   ├── flows/
│   │   └── TASK-XXX/              # Сквозные кросс-платформенные сценарии для TASK-XXX
│   │       └── sequence.svg
│   └── <target>/                  # Целевой узел: web, windows, android, ios, tui и т.д.
│       └── TASK-XXX/              # Изолированный визуальный контракт задачи TASK-XXX (или BUG-XXX)
│           ├── asis.svg           # Исходное состояние до изменений (при редизайне/рефакторинге UI)
│           ├── tobe.svg           # Целевой дизайн-контракт (обязателен для новых и изменяемых экранов)
│           └── <state>.svg        # Опциональные состояния матрицы (empty, loading, error, populated)
│                                  # Для мульти-поверхностных задач: <surface>_asis.svg, <surface>_tobe.svg
├── screenshots/
│   ├── <target>/
│   │   └── TASK-XXX.png           # Постоянный скриншот верификации DoD (<= 2 MB)
│   └── multi-device/
│       └── TASK-XXX.png           # Скриншот верификации связки нескольких узлов
├── diagrams/                      # Архитектурные диаграммы (опционально)
└── design/                        # Материалы дизайн-системы (опционально)
```

### 2.2. Жизненный цикл макетов `As-Is / To-Be`

1. **Greenfield UI (новый экран/компонент):** в каталоге `docs/assets/mockups/<target>/TASK-XXX/` создается целевой макет `tobe.svg` (или `<surface>_tobe.svg`) и, при необходимости, состояния из матрицы 4 состояний (`empty.svg`, `loading.svg`, `error.svg`).
2. **UI Refactoring / Redesign (модификация существующего экрана):** в каталоге `docs/assets/mockups/<target>/TASK-XXX/` фиксируются **оба** состояния — `asis.svg` (текущий вид до правок) и `tobe.svg` (целевой вид после правок). Макетам в папках прошлых задач (`TASK-YYY/`) гарантируется полная иммутабельность.

### 2.3. Укрепление механического контроля в `scripts/kb_lint.py` (Tier 1)

1. **Строгое разрешение путей медиафайлов (Strict Path Resolution):**
   - В `run_linter()` при проверке ссылки на медиафайл, содержащей разделители пути (`/` или `\`), запретить fallback-поиск по голому имени файла (`link_name in file_map`). Ссылка с путем обязана разрешаться строго по относительному пути от заметки, корня `docs/` или корня репозитория.
   - При наличии одноименных файлов (`tobe.svg`, `asis.svg`) в разных папках `TASK-XXX/` битая ссылка на несуществующий `TASK-098/tobe.svg` гарантированно блокирует линтер (Exit code 1).
2. **Контроль топологии `check_asset_layout(docs_dir: Path) -> List[str]`:**
   - Проверяет, что верхнеуровневые директории в `docs/assets/` принадлежат строго множеству `{"mockups", "screenshots", "diagrams", "design"}` (выдает `WARN` при появлении «диких» корней вида `docs/assets/windows/` или неразмеченных файлов в корне `docs/assets/`).
   - Проверяет, что элементы внутри `docs/assets/mockups/<target>/` и `docs/assets/mockups/flows/` (кроме системных dotfiles вроде `.gitkeep`) являются папками, соответствующими шаблону `^(TASK|BUG)-\d{3,}(?:-[a-zA-Z0-9_-]+)?$`.

## 3. Отвергнутые варианты (Rejected Alternatives)

* **Плоское хранение макетов по именам экранов (`docs/assets/mockups/<target>/<screen>_tobe.svg`):**
  * *Причина отклонения:* Вызывает перезапись истории («To-Be Drift») при последующих редизайнах одного и того же экрана в новых фазах, нарушая инвариант постоянных ссылок (Permalinks Principle).
* **Группировка макетов по папкам UI-компонентов без привязки к задаче (`docs/assets/mockups/<target>/<component>/`):**
  * *Причина отклонения:* Не устраняет конфликт версий `tobe.svg` при повторном редизайне компонента через несколько фаз и размывает трассируемость между ТЗ (`TASK-XXX.md`) и его графическими артефактами.
* **Жесткая блокировка (Exit code 1) в `check_asset_layout()` вместо `WARN`:**
  * *Причина отклонения:* Нарушает обратную совместимость на ранее созданных проектах при вызове `install.py --update` и блокирует промежуточные черновики при вставке скриншотов через `Ctrl+V` в Obsidian. Неблокирующий `WARN` для топологии в сочетании с блокирующей проверкой путей ссылок (Exit code 1) обеспечивает оптимальный баланс строгости и DX.

## 4. Последствия

* **Плюсы:**
  * **100% иммутабельность истории дизайна:** ни один редизайн в Фазе $N$ не повреждает визуальные контракты задач из Фаз $1 \dots N-1$.
  * **Когнитивная симметрия для агентов и людей:** единый идентификатор `TASK-XXX` связывает ТЗ, папку макетов и итоговый скриншот.
  * **Ликвидация ложноположительных пропусков в линтере:** одноименные файлы `asis.svg` / `tobe.svg` в разных задачах больше не маскируют битые ссылки.
  * **Защита от «диких» папок:** `check_asset_layout()` мгновенно сигнализирует агенту при попытке создать `docs/assets/<platform>/` мимо `mockups/`.
* **Минусы / Компромиссы:**
  * В ссылках на макеты внутри `PLAN-XXX.md` и `TASK-XXX.md` необходимо всегда указывать путь с подпапкой задачи (`../../assets/mockups/<target>/TASK-XXX/tobe.svg`), а не голое имя `![[tobe.svg]]`.
