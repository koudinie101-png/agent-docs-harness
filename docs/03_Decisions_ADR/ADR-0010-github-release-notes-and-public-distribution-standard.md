# ADR-0010: Стандарт оформления публичных релизов на GitHub и двухформатный экспорт Release Notes

> **Статус:** Принято  
> **Дата:** 2026-10-01  
> **Теги:** #adr #architecture #release-management #github-releases #release-notes #docs-as-code  
> **Первоисточник исследования:** [[../../04_Research/RESEARCH-005-github-release-notes-and-distribution-best-practices|RESEARCH-005: Лучшие практики оформления релизов на GitHub]]  
> **Связанные решения:** [[ADR-0001-zero-dependencies-python-stdlib|ADR-0001: Zero Dependencies]], [[ADR-0007-release-management-dual-mode-and-build-hook|ADR-0007: Release Management]]  

---

## 1. Контекст и проблема

При публикации релиза `v0.5.0` на GitHub было обнаружено, что релиз создался без описания (Release Notes), несмотря на наличие подробного внутреннего документа `docs/02_Tasks/Releases/RELEASE-v0.5.0.md`.

Причины проблемы:
1. **Отсутствие передачи заметок в CI:** В `.github/workflows/release.yml` действие `softprops/action-gh-release@v2` не содержало параметра `body_path` или `body`.
2. **Конфликт форматов:** Внутренний файл релиза в `docs/` содержит YAML frontmatter и относительные викиссылки Obsidian (`[[...]]`), которые в веб-интерфейсе GitHub не распознаются и выглядят как сломанный синтаксис.
3. **Риски доверия и безопасности:** Релизы без описания и таблицы контрольных сумм SHA-256 вызывают недоверие пользователей (риски Supply Chain Security), не информируют подписчиков (Watchers получают пустые email-уведомления) и не содержат инструкций по быстрому обновлению (`curl ... | python3`).

---

## 2. Решение

Утвержден **Стандарт публичного релизного сопровождения** и архитектура двухформатного экспорта (Dual-Format Export):

1. **Двухформатный экспорт в `scripts/kb_release.py`:**
   Утилита выпуска релиза генерирует два независимых артефакта:
   * **Внутренний документ базы знаний:** `docs/02_Tasks/Releases/RELEASE-vX.Y.Z.md` с YAML frontmatter, локальными викиссылками для графа Obsidian и статусом приемки.
   * **Публичные релизные заметки:** `dist/RELEASE_NOTES.md` в чистом формате GitHub Flavored Markdown (GFM):
     - Без YAML frontmatter.
     - Автоматическая конвертация викиссылок в прямые веб-ссылки репозитория на GitHub (`[TASK-017](https://github.com/owner/repo/blob/main/docs/...)`).
     - Блок быстрого старта и обновления (Quick Install / Upgrade snippet).
     - Категоризированный чейнджлог (Features, Fixes, ADRs).
     - Таблица контрольных сумм SHA-256 со сниппетом проверки (`Get-FileHash`).
     - Ссылка на сравнение коммитов (Full Changelog diff URL).

2. **Обязательная передача `body_path` в CI воркфлоу:**
   В шаблоне `.github/workflows/release.yml` фиксируется явная привязка:
   ```yaml
   - name: Publish GitHub Release
     uses: softprops/action-gh-release@v2
     with:
       name: Release ${{ github.ref_name }}
       body_path: dist/RELEASE_NOTES.md
       files: |
         dist/*
   ```

3. **Распространение стандарта через инсталлятор:**
   Обновленный воркфлоу `release.yml` и доработанная утилита `kb_release.py` упаковываются в `install.py` / `build_installer.py`, гарантируя автоматическое качественное оформление релизов во всех дочерних проектах.

## 3. Рассмотренные и отвергнутые варианты (Considered & Rejected Alternatives)

* ❌ **Публикация «голых» релизов без заметок (текущий сбой v0.5.0):**  
  * *Причины отклонения:* Нарушение профессиональных стандартов open-source, дезориентация пользователей, невозможность проверить контрольные суммы и пустые уведомления подписчикам.
* ❌ **Прямая передача внутреннего файла `RELEASE-vX.Y.Z.md` в `body_path`:**  
  * *Причины отклонения:* YAML frontmatter отображается в GitHub Release как некрасивый серый блок кода, а относительные викиссылки `[[...]]` остаются некликабельными.
* ❌ **Опора исключительно на нативный генератор заметок GitHub (`generate_release_notes: true`):**  
  * *Причины отклонения:* GitHub собирает только сырые заголовки PR и коммитов (`fix typo`, `wip`), игнорируя высокоуровневые ТЗ `TASK-XXX`, отчеты `BUG-XXX` и архитектурные решения `ADR-XXXX`, а также не включает таблицу SHA-256.
* ❌ **Ручное заполнение описания релиза через браузер:**  
  * *Причины отклонения:* Человеческий фактор, разрыв сквозной автоматизации и риск забыть обновить релиз после пуша тега.

---

## 4. Обоснование и последствия

### Плюсы:
* **100% автоматизация:** Релиз на GitHub создается автоматически при пуше тега с идеальной версткой, таблицей SHA-256 и кликабельными ссылками.
* **Доверие и безопасность:** Пользователи сразу видят состав изменений и могут верифицировать контрольные суммы скачанных файлов.
* **Сквозная трассируемость:** Публичный релиз на GitHub ссылается прямо на файлы документации Docs-as-Code в репозитории.

### Минусы и риски:
* **Необходимость доработки `scripts/kb_release.py`:** Требуется добавить функцию генерации `dist/RELEASE_NOTES.md` с конвертацией ссылок и обновить инсталлятор.
