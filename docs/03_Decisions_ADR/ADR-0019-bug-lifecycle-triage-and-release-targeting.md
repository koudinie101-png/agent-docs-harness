# ADR-0019: Архитектура жизненного цикла дефектов, изолированный триаж и релизный таргетинг

> **Статус:** Принято | **Дата:** 2026-10-04  
> **Первоисточник исследования:** [[../04_Research/RESEARCH-014-bug-lifecycle-triage-and-release-targeting|RESEARCH-014]]  
> **Связанные ADR:** [[ADR-0009-high-snr-token-architecture-and-context-efficiency|ADR-0009]], [[ADR-0010-github-release-notes-and-public-distribution-standard|ADR-0010]], [[ADR-0016-single-task-execution-barrier-and-stop-on-complete-protocol|ADR-0016]]  

---

## 1. Контекст и проблема

В текущей инфраструктуре Docs-as-Code зафиксированы критические проблемы обработки дефектов:
1. **Eager Auto-Fixing Runaway:** При вызове `/kb-bug` агент не останавливается после фиксации отчета, а сразу приступает к изменению исходного кода и прогону тестов, нарушая автономию разработчика и инвариант единичной задачи.
2. **Непрозрачность релизного таргетинга:** В отчетах `BUG-XXX` нет полей `target_release`, `target_phase`, `release_blocker`, `fixed_in`. Неясно, в какой релиз пойдет исправление.
3. **Хроническая утечка в релизных заметках:** `scripts/kb_release.py` агрегирует все закрытые баги из каталога `docs/02_Tasks/Bugs/` без фильтрации по текущей версии, из-за чего старые баги дублируются во всех последующих релизах.
4. **Контекстное ограничение:** Изменение скилла `/kb-bug` не должно раздувать контекстную нагрузку (High-SNR Token Budget).

---

## 2. Принятое решение

1. **Разделение фаз Заведения (Triage) и Исполнения (Implementation):**
   - Скилл `.agents/skills/kb-bug/SKILL.md` рефакторится строго в инструмент **Режима 2B (Defect Logging & Interactive Triage)**. Из него полностью удаляются любые инструкции по редактированию кода и прогону тестов.
   - Вводится обязательный терминальный барьер `Stop & Yield Control`: после записи отчета, обновления `Kanban.md` и Git-коммита агент прекращает вызовы инструментов и выводит разработчику структурированные варианты действий (`/kb-implement BUG-XXX`, включение в фазу или бэклог).
2. **Унификация Режима 3 для багов через `/kb-implement BUG-XXX`:**
   - Скилл `.agents/skills/kb-implement/SKILL.md` расширяется для приема идентификатора `BUG-XXX` в качестве цели выполнения.
   - При передаче бага агент исполняет строгий цикл TDD: **RED (падающий тест из `regression_test`) $\to$ GREEN (исправление кода) $\to$ REFACTOR $\to$ `kb-complete`**.
   - Это исключает дублирование правил коммита, верификации и линтинга в двух разных скиллах и экономит до 60% контекста при триаже.
3. **Релизный контракт в `TEMPLATE_BUG.md`:**
   В YAML frontmatter шаблона дефекта добавляются обязательные атрибуты:
   - `target_release: "vX.Y.Z" | "hotfix" | "backlog"`
   - `target_phase: N | null`
   - `release_blocker: true | false`
   - `fixed_in: null` (заполняется автоматически при закрытии дефекта).
4. **Точная фильтрация в релизном пайплайне (`scripts/kb_release.py`):**
   В чейнджлог релиза включаются только те дефекты со статусом `fixed`, у которых `fixed_in == target_version` либо `target_phase == current_phase` (при отсутствии `fixed_in`).

---

## 3. Отвергнутые варианты (Rejected Alternatives)

* ❌ **Создание отдельного тяжелого скилла `/kb-fix`:** Отклонено, так как исправление бага идентично реализации спецификации по стандарту Режима 3. Дублирование конвейера коммитов и проверок нарушает принцип DRY и раздувает реестр скиллов.
* ❌ **Монолитный `kb-bug` с CLI-флагами `--log` и `--fix`:** Отклонено, так как сохранение процедур исправления кода в одном файле провоцирует LLM на срыв барьера остановки при фоновом сжатии контекста.
* ❌ **Фильтрация багов по датам коммитов в `kb_release.py`:** Отклонено из-за нестабильности дат в Git (rebase, cherry-pick) и нарушения принципа декларативности базы знаний.

---

## 4. Последствия

* **Плюсы:**
  - 100% защита от случайного немедленного исправления кода.
  - Прозрачность планирования: разработчик всегда видит, блокирует ли баг релиз и в какую версию он запланирован.
  - Чистые Release Notes на GitHub без дублирования исторических дефектов.
  - Сокращение расхода токенов на 40% при вызове `/kb-bug` за счет выноса кода фикса в `kb-implement`.
* **Минусы / Компромиссы:**
  - Исправление дефекта теперь требует явного второго шага от пользователя (`/kb-implement BUG-XXX`), что является осознанным компромиссом ради управляемости и безопасности.
