# ADR-0016: Барьер единичной задачи и протокол гарантированной остановки (Single-Task Execution Barrier)

> **Статус:** Принято | **Дата:** 2026-10-02

## 1. Контекст и проблема

В ходе реализации проектных фаз с участием AI-агентов выявлена системная уязвимость: при достижении лимита контекста среда производит сжатие истории диалога (`<CONTEXT_SUMMARY>`). В процессе сжатия теряются исходные модальные ограничения пользователя (*«сделай только задачу N»*), а резюме содержит список последующих шагов (*«Next Steps: 1. Commit N, 2. Implement N+1, 3. Implement N+2»*).

Агент, не имея явного запрета на переход между задачами, воспринимает этот блок как собственную исполнительную очередь и автономно закрывает задачи `N+1` и `N+2` без ведома и одобрения человека (**Eager Task Chaining / Autonomous Pipeline Runaway**). Это нарушает главный принцип парного программирования — поэтапный человеческий контроль (Human-in-the-Loop).

---

## 2. Решение

Принят трехуровневый стандарт эшелонированной защиты (Defense-in-Depth):

### 2.1. Инвариант единичной задачи в `AGENTS.md`
В корневые правила `AGENTS.md` вносится жесткий инвариант:
* **Single-Task Execution Barrier:** Команда `/kb-implement <TASK-XXX>` авторизует работу **строго над одной** конкретной спецификацией задачи.
* **Запрет авто-чейнинга:** Даже если в плане, бэклоге или Devlog перечислены следующие задачи, агенту **категорически запрещено** начинать их реализацию в той же сессии без явной команды пользователя вида `/kb-implement TASK-YYY`.
* Любые секции «Следующие шаги» в планах, канбане и сводках носят **исключительно информационный характер для разработчика** и не являются исполнительным мандатом для агента.

### 2.2. Терминальный шаг «Stop & Yield Control» в скиллах
В скиллах `.agents/skills/kb-implement/SKILL.md` и `.agents/skills/kb-complete/SKILL.md` закрепляется обязательный терминальный шаг:
1. Завершить коммит и верификацию текущей задачи.
2. Сформировать ответ пользователю согласно Anti-Echo протоколу (ссылка на файл, 3–5 пунктов резюме).
3. Предложить следующую команду человеку.
4. **Принудительно прекратить любые вызовы инструментов (Tool Calls).** Передать управление человеку и ожидать ввода.

### 2.3. Семантическое разделение субъекта в `Devlog.md`
Формулировка «Следующий шаг» в журнале разработки заменяется на эксплицитно ориентированную на человека:
* Было: `- **Следующий шаг:** Реализация задачи TASK-XXX.`
* Стало: `- **Рекомендуемый следующий шаг (Ожидает команды пользователя):** \`/kb-implement TASK-XXX\`.`

## 3. Отвергнутые варианты (Rejected Alternatives)

* ❌ **Полноценный автономный пакетный запуск («Batch Agent Mode»):**  
  *Причина отказа:* Противоречит философии Docs-as-Code. Разработчик должен валидировать архитектурные решения и diff каждой задачи перед тем, как система пойдет дальше.
* ❌ **Блокирующий pre-commit hook в Git:**  
  *Причина отказа:* Ограничение тулинга мешает человеку вносить пакетные правки опечаток или документации напрямую. Проблема лежит в поведении агента, а не в ограничениях Git.
* ❌ **Удаление навигационных ссылок на следующие задачи:**  
  *Причина отказа:* Разрушает целостность базы знаний и ухудшает обзор дорожной карты для разработчика.

---

## 4. Последствия

### Плюсы:
1. **100% предсказуемость:** Агент гарантированно останавливается после выполнения одной задачи.
2. **Устойчивость к сжатию контекста:** Даже если в сводке сжатия перечислен весь бэклог, инвариант запрещает агенту брать следующую задачу без промпта.
3. **Экономия токенов:** Исключаются случайные несанкционированные прогоны и переделки.

### Минусы / Компромиссы:
1. Пользователю требуется отправлять команду для каждого шага конвейера (что соответствует целевому процессу Human-in-the-Loop).
