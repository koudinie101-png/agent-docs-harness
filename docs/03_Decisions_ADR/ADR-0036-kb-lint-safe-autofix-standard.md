# ADR-0036: Архитектурный стандарт безопасного автофикса в kb_lint.py (--fix, --write, Zero Data Loss)

> **Статус:** Принято | **Дата:** 2026-11-19  
> **Первоисточник исследования:** [[../04_Research/RESEARCH-030-kb-lint-safe-autofix|RESEARCH-030: Архитектура безопасного автофикса]]  
> **Связанные решения:** [[ADR-0001-zero-dependencies-python-stdlib|ADR-0001: Zero Dependencies]], [[ADR-0032-machine-readable-lint-contract-and-rule-registry|ADR-0032: Машинный контракт линтера]], [[ADR-0035-wave-1-deterministic-navigation-and-task-graph-standard|ADR-0035: Стандарт навигации и графа зависимостей Волны 1]]

## 1. Контекст и проблема

Инструмент `scripts/kb_lint.py` продуктов первого уровня (Tier 1 Quality Gate) выявляет нарушения целостности базы знаний (правила `KB-001`…`KB-015`), формирует машинно-читаемые отчёты (`--format {text,json,sarif}`) и контролирует граф зависимостей (`KB-010`).

Однако отсутствие возможности автоматического устранения нарушений заставляет разработчиков и AI-агентов вручную править мелкие синтаксические дефекты:
- отсутствие обязательного поля `depends_on: []` в спецификациях;
- неконсистентные форматы дат (`YYYY.MM.DD` вместо ISO-8601 `YYYY-MM-DD`);
- висячие пробелы (trailing spaces) и отсутствие завершающего перевода строки (`\n` EOF);
- искажения маркеров `---` в YAML frontmatter.

Ручное исправление этих дефектов приводит к лишним раундтрипам контекста агентов и снижает скорость разработки. При этом внедрение автофикса несёт критический риск: неаккуратная перезапись Markdown-файлов может удалить пользовательские комментарии, исказить разметку или привести к потере данных (Data Corruption).

---

## 2. Решение

Утвердить архитектурный стандарт безопасного автофикса для `scripts/kb_lint.py`:

### 2.1. Таксономия исправляемости (Fixability Taxonomy)
Правила строго делятся на исправляемые автоматически и категорически запрещённые к автофиксу:

1. **Разрешённые к автофиксу (Safe Deterministic Fixes):**
   - `KB-004` (Frontmatter delimiters): нормализация разделителей `---` (устранение лишних пробелов, закрытие блока).
   - `KB-005` (Date normalization): приведение дат в полях `created`, `updated`, `date` к стандарту ISO-8601 (`YYYY-MM-DD`).
   - `KB-006` (Trailing whitespaces): удаление концевых пробелов во всех строках файла.
   - `KB-007` (EOF newline): гарантия наличия ровно одного завершающего перевода строки `\n`.
   - `KB-010` (Default field injection): безопасная вставка `depends_on: []` перед закрывающим `---` во frontmatter спецификаций задач (`02_Tasks/Specs/`), если поле отсутствует.

2. **Категорически запрещённые к автофиксу (Unsafe / Ambiguous Fixes):**
   - `KB-001` (Broken wikilinks): запрещено угадывать целевые заметки (fuzzy match).
   - `KB-002` (Missing full frontmatter): запрещено генерировать контент заметок без участия автора.
   - `KB-003` (Broken anchors): запрещено произвольно менять заголовки.
   - `KB-010` (Dependency cycles & dangling IDs): запрещено автоматически разрывать циклы зависимостей.

### 2.2. Модель хирургического строкового патчинга (Surgical String Patching)
- Модификация файлов выполняется **без сторонних библиотек (Zero-Deps)** и без полной десериализации/сериализации документов.
- Применяется точечная модификация строк (строковый diff/инъекция) с сохранением 100% пользовательских комментариев, порядка полей и исходных отступов.
- Каждое исправление регистрируется объектом `Fix` с указанием правила, описания, строки и заменяемого текста.

### 2.3. Протокол безопасности (Safety & Zero Data Loss)
- **Safe Preview по умолчанию:** Запуск `python scripts/kb_lint.py --fix` работает в режиме предварительного просмотра (`--dry-run`), выводя цветной унифицированный дифф (`unified_diff`) и список запланированных изменений.
- **Явное подтверждение записи (`--write`):** Модификация файлов на диске выполняется только при явном указании флага `--write` (например, `python scripts/kb_lint.py --fix --write`).
- **Атомарная запись:** Запись изменений производится через временный файл в целевой директории с последующей атомарной заменой через `os.replace()`.
- **Защита от несохранённых изменений (Git-Clean Guard):** При обнаружении незакоммиченных изменений в файле линтер пропускает его, если не передан флаг `--allow-dirty`.

### 2.4. Выходные контракты (CLI & Machine-Readable Output)
- В текстовом режиме (`--format text`): вывод понятного диффа и итоговой строки:
  `Fixed 4 issues in 2 files (dry-run). Run with --write to apply.`
- В JSON/SARIF режимах: каждый объект `Finding` содержит булево поле `fixable: true/false` и блок `fix: { "description": "...", "diff": "..." }`.

## 3. Отвергнутые варианты (Rejected Alternatives)

* ❌ **Использование внешних парсеров (`ruamel.yaml`, `markdown-it`, `tree-sitter`):**  
  Отклонено. Нарушает фундаментальный принцип независимости от сторонних зависимостей ([[ADR-0001-zero-dependencies-python-stdlib|ADR-0001]]). Усложняет дистрибуцию через автономный монолит `install.py`.
* ❌ **Полная перезапись YAML через словарь парсера:**  
  Отклонено. Удаляет все комментарии пользователей (`# depends_on: []`), произвольно меняет порядок ключей и разрушает верстку заметок.
* ❌ **Запись на диск без подтверждения (флаг `--fix` пишет сразу без `--dry-run`):**  
  Отклонено. Создаёт неприемлемый риск непреднамеренной порчи репозитория. Safe-by-default — обязательное требование для систем управления документацией как кодом.
* ❌ **Нечёткий автофикс битых ссылок (Fuzzy Link Matching):**  
  Отклонено. Может незаметно исказить семантику архитектурных документов и спецификаций.

## 4. Последствия

### Плюсы:
- Мгновенное устранение рутинных ошибок форматирования и структуры базы знаний за один вызов.
- Сокращение времени онбординга и расхода токенов AI-агентов при создании новых файлов.
- Абсолютная сохранность пользовательских комментариев и форматирования при автофиксе.
- Полная прозрачность изменений благодаря встроенному генератору диффов (`--dry-run`).
- Zero-Dependencies: сохраняется монолитность и автономность `kb_lint.py`.

### Минусы / Компромиссы:
- Узкий первоначальный скоуп автофикса (только 5 детерминированных правил); сложные семантические ошибки по-прежнему требуют внимания разработчика.
- Необходимость передачи флага `--write` для применения изменений добавляет одно дополнительное действие, что оправдано безопасностью данных.
