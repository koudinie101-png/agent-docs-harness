# 🚀 Мастер-спецификация: agent-docs-harness

> **Проект:** `agent-docs-harness`  
> **Тип:** Автономный CLI-инструмент и фреймворк дисциплин AI-агентов  
> **Лицензия:** MIT  
> **Связанные документы:** [[docs/00_Index|00_Index]], [[docs/Onboarding|Онбординг]], [[docs/02_Tasks/Kanban|Канбан]], [[docs/02_Tasks/Roadmap|Дорожная карта]].

---

## 1. Концепция и цель проекта

### Проблема
При разработке с AI-агентами (Cline, Roo Code, Claude Code, Cursor, Copilot) разработчики неизбежно сталкиваются с тремя критическими проблемами:
1. **«Амнезия контекста»:** агент забывает договоренности, архитектурные ограничения и решения, принятые 20 сообщений назад.
2. **«Самовольная ломка кода»:** агент бросается писать код без предварительного согласования архитектуры, ломая существующие контракты и плодя скрытые баги.
3. **«Расползание архитектуры (Link Rot & Arch Drift)»:** проект обрастает устаревшими markdown-файлами с битыми ссылками, а решения нигде не фиксируются.

### Решение
`agent-docs-harness` — это автономный кроссплатформенный установщик (Zero Dependencies, Python 3), который разворачивает в любом проекте профессиональную инфраструктуру **Docs-as-Code** и строгий **3-режимный процесс взаимодействия с агентами**:

```bash
curl -sSL https://raw.githubusercontent.com/koudinie101-png/agent-docs-harness/main/install.py | python3
```

## 2. Ключевые компоненты харнесса

### 2.1. База знаний Docs-as-Code (`docs/`)
Структурированное хранилище (Obsidian Vault) внутри репозитория:
* `00_Templates/` — 12 эталонных шаблонов (ADR, Research, Task, Plan, Bug, Test, Onboarding, Index, Kanban, Roadmap, Devlog, Architecture) с поддержкой YAML frontmatter.
* `01_Architecture/` — схемы, архитектурные контракты и протоколы.
* `02_Tasks/` — Канбан-доска (`Kanban.md`), Дорожная карта (`Roadmap.md`), планы (`Plans/`), спецификации задач (`Specs/`) и баг-трекер (`Bugs/`).
* `03_Decisions_ADR/` — Архитектурные решения (`ADR-XXXX`) с фиксацией отклоненных альтернатив.
* `04_Research/` — Исследования платформенных граблей, памяти и фоновых режимов (`RESEARCH-XXX`).
* `05_Testing/` — Сценарии приемочного тестирования (E2E UX).
* `Devlog.md` — Хронологический журнал сессий разработки.
* `Onboarding.md` — Единое руководство разработчика и агента.
* `00_Index.md` — Карта заметок (Map of Content).

### 2.2. Цветовая дифференциация Obsidian Graph (`.obsidian/graph.json`)
7 цветовых групп для визуализации архитектурных связей:
* ⚪ **Белый:** Главные хабы (`00_Index`, `Devlog`, `SPEC`, `Onboarding`).
* 🟣 **Фиолетовый:** Архитектура (`01_Architecture`).
* 🔵 **Голубой/Циан:** Решения (`03_Decisions_ADR`, `#adr`).
* 🟡 **Желтый/Янтарный:** Исследования платформы (`04_Research`, `#research`).
* 🟠 **Оранжевый:** Задачи, планы и roadmap (`02_Tasks`, `#task`).
* 🔴 **Красный:** Баги и дефекты (`02_Tasks/Bugs`, `#bug`).
* 🟢 **Зеленый:** Приемочное тестирование (`05_Testing`, `#testing`).

### 2.3. Автономный линтер (`scripts/kb_lint.py`)
* Zero dependencies (только Python 3 stdlib: `pathlib`, `re`, `argparse`).
* Валидация всех вики-ссылок `[[...]]`, регистра имен и структуры путей.
* Проверка наличия и валидности YAML frontmatter в задачах, багах, планах и ADR.
* Кроссплатформенный вывод в UTF-8.

### 2.4. Дисциплина 3 режимов и конфигурация агентов
* Единый корневой файл правил **`AGENTS.md`**.
* Адаптеры/зеркала под популярные среды:
  * `.clinerules` (VS Code Cline / Roo Code).
  * `CLAUDE.md` (Anthropic Claude Code в терминале VS Code).
  * `.cursorrules` (Cursor IDE).
  * `.github/copilot-instructions.md` (GitHub Copilot).
* **3 жестких режима:**
  * **Режим 1: Планирование (Planning / RFC)** — только обсуждение, аргументированная критика, оценка рисков. Запрет на редактирование кода!
  * **Режим 2: Формирование ТЗ (Task Spec)** — список файлов `[NEW]`/`[MODIFY]`, контракты, DoD, план верификации. Запрет на редактирование кода!
  * **Режим 3: Реализация (Implementation)** — написание кода строго по ТЗ, прогон тестов, закрытие задачи в Канбане и Devlog.
* **Принцип неизменяемости ссылок (Permalinks):** задачи и баги не перемещаются в архивные папки при закрытии.
* **Regression-First:** баги закрываются только при наличии подтверждающего автотеста.

## 3. Архитектура инсталлятора `install.py`

### 3.1. Требования к рантайму
* Только стандартная библиотека Python 3 (Python 3.8+).
* Никаких внешних пакетов (`no requests`, `no pyyaml`, `no rich`).
* Полная автономность (Self-Contained) — скрипт содержит в себе упакованные шаблоны и код линтера.
* Кроссплатформенная работа (macOS, Linux, Windows).

### 3.2. Режимы запуска
1. **Интерактивный мастер (Interactive Wizard):**
   * Определение имени проекта (дефолт — имя текущей папки).
   * Выбор технологического стека (Swift/iOS/macOS, Web/TypeScript, Python, .NET, Generic).
   * Выбор целевого агента / редактора (All, Cline, Claude Code, Cursor, Copilot, Generic).
   * Выбор стратегии Git (GitHub, Local-Only, Skip).
2. **Неинтерактивный CLI (Flags / Automation):**
   * `--name <str>` — название проекта.
   * `--stack {swift,ts,python,dotnet,generic}` — предустановка стека.
   * `--agent {all,cline,claude,cursor,copilot,generic}` — конфигурации агентов.
   * `--git {github,local,none}` — стратегия контроля версий.
   * `-y`, `--yes`, `--non-interactive` — авто-подтверждение дефолтов.
   * `--target-dir <path>` — путь назначения (по умолчанию `.`).

## 4. План фаз разработки

* **Фаза 1: Спецификация и базовый каркас** — Dogfooding `docs/`, `SPEC.md`, `kb_lint.py`.
* **Фаза 2: Архитектура инсталлятора и генерация шаблонов** — реализация `install.py` со встроенными шаблонами и адаптацией под стеки (Swift, TS, Python, .NET, Generic).
* **Фаза 3: Интерактивный мастер и CLI интерфейс** — поддержка интерактивного ввода и CLI флагов.
* **Фаза 4: Верификация, E2E-тесты и документация** — запуск в тестовой песочнице, проверка `kb_lint.py`, подготовка `README.md`.
